The C-Chain VM is avalanchego's own since the coreth repo was archived. From Helicon (2026-09-22) it is the SAE VM (vms/saevm, ACP-194), and v1.15.3 registers saevm.Factory directly. No Coreth execution path is left in the tree: graft/coreth keeps only params, header types, the precompiles and nativeasset. Like coreth before it, the VM is NOT a whole-repo geth fork. It consumes ava-labs/libevm — a geth fork published as a library with explicit extension hooks — and layers Avalanche behaviour through RulesExtra hooks (graft/coreth/params/hooks_libevm.go, vms/saevm/cchain/libevm). Structurally the cleanest fork relationship in this dataset: divergence is concentrated in hook implementations rather than scattered through a patched tree.

Fork names and EIP sets diverge in both directions#

Fork names are recorded as claims; the eips: map is the measurement. The two diverge in both directions.

Avalanche has P256VERIFY (an Osaka feature) without BLS12-381 (a Prague feature), so no mainnet fork name describes its EIP set.

At least thirteen ways a chain decides a feature is active#

"When does feature X become active on chain Y" has no general answer. Mainnet uses a timestamp; reading a fork timestamp is not a portable method, because on much of this dataset there is no timestamp and on some of it no client-side schedule to read at all.

Aliases mainnet fork names onto its own timestamps (ShanghaiTime = durango), so the mainnet name is a label, not a schedule.

Transactions outside the EIP-2718 envelope#

Not every transaction a chain executes carries an EIP-2718 type byte. The ones that do not need their own non_evm_transactions section, and an indexer enumerating through the EVM envelope does not see them.

The atomic import and export transactions (UTXO, Avalanche codec) carry no type byte, so an indexer reading the EVM envelope does not see the chain's cross-chain value movement at all.

Tombstoned precompile addresses#

A tombstoned address is kept alive as an always-reverting stub rather than removed, so it is permanently consumed — and it fails differently from an absent one, which returns success with empty output. Two chains adopted the pattern independently.

The native-asset trio at 0x0100..00-02 is the clearest example in the dataset of precompile addresses being permanently consumed: they cannot be reused and cannot be removed, only made to revert.

eth_getCode cannot tell a precompile from a contract#

SCHEMA.md distinguishes a precompile (native code, no bytecode in state) from a system contract (real bytecode at a fixed address), and the obvious test is eth_getCode: empty means precompile. That test fails on eight rows here, in six shapes, in BOTH directions. Classification has to come from the client's precompile map; a probe can only corroborate it.

ApplyPrecompileActivations deliberately writes nonce=1, code=0x01 at its precompiles so Solidity's extcodesize guard passes — the origin of the pattern several rows here inherit.

Transaction authorization#

Key bindingderived
Signers per tx1 for EVM transactions; N for atomic transactions
Note

TWO AUTHORIZATION MODELS ON ONE CHAIN, and only one of them is Ethereum's. EVM transactions are stock: TransactionToMessage calls libevm's types.Sender, secp256k1, one signer, address = hash of the recovered key. The ATOMIC transactions already recorded in non_evm_transactions are authorized completely differently. They are not RLP, carry no type byte, and are not signed with an Ethereum digest. The signed payload is the Avalanche-codec serialization of the UNSIGNED transaction, hashed by avalanchego's hashing.ComputeHash256 rather than keccak256 over an EIP-155/EIP-2718 envelope, and the signature block is not a single (v,r,s) but a LIST OF CREDENTIALS — Tx.Creds — one per input, each holding a list of signatures. The count of signers is therefore a property of the transaction, not of the chain: an export with five EVMInputs owned by five different accounts is one transaction with five independent signers, and an import spending an m-of-n threshold UTXO needs m signatures for that one input alone. This is the same curve as an EVM transaction and a fundamentally different authorization envelope. signers_per_tx is written as prose because a single integer would be false for one of the two paths. Warp's BLS12-381 is the trap in this row and is recorded as authorizes: never.

secp256k1_utxo_credentialprotocol0x01
The atomic import/export path. Same curve, different everything else. EXPORT: one credential per EVMInput, each required to hold EXACTLY ONE signature (errIncorrectNumSignatures otherwise), recovered against utx.Bytes() and checked against that input's declared Address via pubKey.EthAddress(). Multiple distinct accounts can be debited by one transaction, each authorizing only its own input. IMPORT: one credential per imported UTXO, verified by Fx.VerifyTransfer against the UTXO's own secp256k1fx output owners — an m-of-n threshold multisig defined on the SOURCE chain (X or P). For those inputs the key binding is effectively `declared`, not `derived`: the addresses and threshold that may spend are written into the UTXO, not derived from any C-Chain account. PRECOMPILE PAIRING, STATED CAREFULLY. This is NOT an `authorizes: protocol` + `precompile: none` finding. The scheme is secp256k1 ECDSA, and 0x01 verifies secp256k1 ECDSA, so a contract that reconstructs the digest can check these signatures. The catch is the digest: it is SHA-256 of the Avalanche-codec bytes of the unsigned transaction. RecoverPublicKey hashes with hashing.ComputeHash256 before recovering, which the avalanchego re-pin now lets this row verify. It is not keccak256 of an RLP envelope, so a contract must rebuild the codec bytes and SHA-256 them (0x02) before calling 0x01. Recorded as 0x01 with that caveat rather than as `none`.

Ordering & execution 2#

QuestionVerdictWhat happens
Ordered, then invalidunreachable

SAME VERDICT, NEW MECHANISM SINCE HELICON. The SAE builder no longer executes a transaction to include it: it applies each candidate to a worst-case balance and nonce state designed so that everything included is valid when the execution stream reaches it. The ordered-but-invalid state stays unreachable. Before Helicon (Coreth): the proposer executes each transaction as it appends it: an invalid one is popped out of the candidate set and never reaches the block, so the ordered-but-invalid state is not reachable and the nonce is untouched. If one reached a proposed block anyway, preCheck fails at import and the whole block is invalid. Mainnet semantics, verified against this row's own pinned client rather than assumed from the family.

Max transaction128 KiBpolicy

The flat cap is libevm's geth value (4 * 32 KiB), at the libevm version avalanchego v1.15.3 pins. It is no longer the binding rule. Since Helicon the gossip layer also requires gasLimit >= ceil(size * blockGasLimit / TargetBlockBytes): at 80M gas and 1.75 MiB that is about 43.6 gas per byte, so a transaction heavy on calldata but light on gas is refused far below 128 KiB. This keeps a full block inside one p2p message. TargetBlockBytes is marked "NOT a consensus-breaking change", so this is builder and mempool policy, not block validity.

NOT DEVP2P. Gotchas 5#

  • NO EIP-7702. The C-Chain is Cancun-equivalent, not Prague — tx type 0x04 does not exist and no BLS12-381 precompiles are available. Wallets and AA stacks that assume Prague on any major EVM chain break here.
  • P256VERIFY at 0x0100 exists WITHOUT BLS12-381 at 0x0b-0x11, because it arrived via Avalanche's own Granite fork rather than Osaka. Inferring a chain's fork level from which precompiles are present fails in both directions on this chain.
  • Three precompile addresses (0x0100..00/01/02) are tombstoned: they always revert. They are neither absent nor functional — calling them fails differently than calling an empty account, which returns success.
  • Atomic import/export transactions are not RLP and have no EIP-2718 type byte. Any indexer that enumerates "all transactions in a block" via the EVM envelope silently misses all cross-chain value movement.
  • Cancun header fields are present but pinned to constants. blobGasUsed == 0 is enforced, not conventional — contrast OP Stack, which repurposed the same field to mean something else entirely.

Full write-up#

Chain ID 43114 · role: fork · upstream: go-ethereum (via libevm) · baseline: Cancun

Reference: ava-labs/avalanchego v1.15.3 @ 983815fd. Re-pinned on 2026-11-23 from ava-labs/coreth v0.16.0, which was archived on 2025-11-25 when coreth moved into avalanchego.

Since Helicon (2026-09-22 15:00 UTC, block 95921105) execution is asynchronous

The C-Chain VM is now the SAE VM (vms/saevm, ACP-194). In v1.15.3 it is registered directly: no Coreth execution path is left in the tree. What callers see:

  • A header's stateRoot is the root of the last settled block, not of the block itself.
  • "latest" means the last executed block; "safe" and "finalized" mean the last settled one.
  • Every transaction pays for at least ceil(gasLimit/2). This shows in live receipts.
  • Atomic import/export transactions run as end-of-block operations. Their gas counts in gasUsed, so extDataGasUsed is 0.
  • New header fields targetExponent and minPriceExponent carry the validator-voted gas target and the ACP-283 minimum price.
  • The gas limit is 80M, and blocks average under a second.

Still true: Cancun only, no Prague or Osaka, PREVRANDAO = 1, and the three tombstoned native-asset precompiles.

Headline: no Prague, no Osaka

vms/saevm/cchain/genesis.go:100-101 assigns exactly two Ethereum fork times (coreth's params/config_extra.go did the same before Helicon):

c.ShanghaiTime = utils.NewUint64(*durango)
c.CancunTime   = utils.NewUint64(*etna)

There is no PragueTime or OsakaTime assignment anywhere in the tree. The C-Chain is Cancun-equivalent. Consequences:

  • No EIP-7702. Tx type 0x04 does not exist. The most consequential absence here for wallets and account-abstraction tooling.
  • No BLS12-381. Precompiles 0x0b–0x11 are absent.
  • No EIP-2935 history, no EIP-7002/7251 queues, no deposit contract — all Prague, and all meaningless without a beacon chain anyway.

…yet P256VERIFY is present, via a different fork entirely

PrecompiledContractsGranite (params/hooks_libevm.go:81-86) adds P256VERIFY at 0x0100 — through Granite, an Avalanche upgrade, not through Osaka.

So the C-Chain has 0x0100 but not 0x0b–0x11, inverting mainnet's order: mainnet shipped BLS12-381 at Prague, two forks before P256VERIFY at Osaka. Inferring fork level from precompile presence fails in both directions on this chain. This is the second chain in the dataset (after OP Stack) to hold 0x0100 under a non-Osaka fork, which retires the idea that 0x0100 implies anything about lineage.

Cancun adopted structurally, then hollowed out

The SAE block builder (vms/saevm/cchain/hooks.go) writes these, and a block is verified by rebuilding it. Before Helicon, coreth's wrapped_block.go enforced the same constraints. Once Cancun is active:

Field Constraint Effect
blobGasUsed must be 0 errBlobsNotEnabled
excessBlobGas must be 0 no blob fee market
parentBeaconRoot must be the empty hash no beacon chain to root

The header conforms to Cancun's shape while every Cancun-specific field is pinned to a constant. Blob transactions (0x03) exist as a libevm type but can never be included.

Worth contrasting with OP Stack, which took the same field, blobGasUsed, and repurposed it to mean DA footprint. Two chains, one field, three meanings across the dataset. Anyone reading blobGasUsed cross-chain needs a per-chain decoder.

Three tombstoned precompile addresses

Address Was Now
0x0100…0000 GenesisContract always reverts
0x0100…0001 NativeAssetBalance always reverts
0x0100…0002 NativeAssetCall always reverts

Live in Apricot Phase 2, again in Phase 6, tombstoned at Banff. DeprecatedContract returns vm.ErrExecutionReverted unconditionally (nativeasset/contract.go:167-171).

These addresses are permanently consumed — they can be neither reused nor removed, only made to fail. And they fail differently from an empty account: calling an address with no code succeeds and returns nothing; calling these reverts. A contract probing for feature support gets opposite answers.

Warp: a precompile with no mainnet analogue

0x0200…0005 is the Avalanche Warp Messaging precompile (Durango). It reads block predicates via GetPredicateResults — results computed outside normal EVM execution and made available to the precompile. There is no mainnet equivalent to this mechanism, so it is not expressible as a delta on any Ethereum concept.

Note the two separate custom ranges — 0x0100…00-02 and 0x0200…05 — both far from mainnet's 0x01–0x11. Avalanche followed the placement convention.

Atomic transactions live outside the envelope

UnsignedImportTx and UnsignedExportTx (plugin/evm/atomic/) move value between the C-Chain and Avalanche's X/P chains. They are UTXO-based, serialised with Avalanche's own codec, not RLP, and registered in a separate codec namespace (codec.go:33-34) — entirely outside EIP-2718 while still included in C-Chain blocks.

They have no type byte, so they cannot be represented in tx_types at all. This forced a new non_evm_transactions section in the schema. An indexer that enumerates "all transactions in a block" through the EVM envelope silently misses all cross-chain value movement on the C-Chain.

Architecture note

The C-Chain VM (coreth until Helicon, SAE since) is not a whole-repo geth fork. It consumes ava-labs/libevm — a geth fork published as a library with explicit extension hooks — and layers Avalanche behaviour through RulesExtra hooks in graft/coreth/params/hooks_libevm.go and vms/saevm/cchain/libevm. This is the cleanest fork relationship in the dataset: divergence is concentrated in hook implementations rather than scattered through a patched tree, which is why the precompile deltas above could be read off a single 90-line file.

Fees

London is active (LondonBlock = 0 from Apricot Phase 3), so 1559-shaped fields exist, but the base-fee update rule is Avalanche's own ACP-176 target-gas-excess mechanism (vms/saevm/gastime/acp176.go), not mainnet's. Since Helicon it also has ACP-283's dynamic minimum price, and every transaction pays at least half its gas limit.

Two authorization models, one chain

The C-Chain is the only row in this cluster where how a transaction is authorized depends on which kind of transaction it is.

EVM transactions are mainnet's: TransactionToMessage → libevm's types.Sender, secp256k1, one signer, address = hash of the recovered key.

Atomic transactions — the import/export pair already recorded in non_evm_transactions — use the same curve and nothing else in common:

EVM transaction atomic transaction
signed payload RLP, EIP-155/2718 envelope Avalanche codec, unsigned-tx bytes
digest keccak256 hashing.ComputeHash256
signature block one (v, r, s) Tx.Creds — a list of credentials, one per input, each a list of signatures
signers 1 one per input, and m per m-of-n threshold UTXO
key binding derived derived on export, declared on import

On export, each EVMInput carries its own Address and needs exactly one signature, recovered against utx.Bytes() and matched with pubKey.EthAddress(). Five inputs owned by five accounts is one transaction with five independent signers — something the EVM envelope cannot express at all.

On import, credentials are checked by Fx.VerifyTransfer against the source-chain UTXO's own secp256k1fx output owners: an m-of-n threshold multisig declared on the X- or P-Chain, not derived from any C-Chain address.

Not an unpaired scheme — stated so nobody has to re-derive it

The scheme is still secp256k1 ECDSA and 0x01 still verifies secp256k1 ECDSA, so this is not the authorizes: protocol + precompile: none case. The catch is the digest: a contract wanting to check an atomic credential has to reconstruct Avalanche codec bytes and hash them with ComputeHash256 (in avalanchego, outside the pinned clone) rather than keccak an RLP envelope.

Warp's BLS is consensus signing

The aggregated BLS12-381 signature on a Warp message is verified by Config.VerifyPredicate — a block predicate evaluated outside EVM execution. The precompile at 0x0200…05 only reads the result. It authorizes a message, never a transaction, and it is not a general-purpose BLS verifier a contract can point at arbitrary signatures.
