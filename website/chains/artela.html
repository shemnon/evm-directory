A Cosmos SDK L1 whose EVM module is a RENAMED FORK OF ETHERMINT — the same tree cosmos/evm descends from — carrying one feature no other row in this dataset has: ASPECTS. An Aspect is a WASM module registered on-chain and BOUND TO A CONTRACT BY THAT CONTRACT'S OWNER, which the protocol then invokes at five join points around EVM execution. It can abort a transaction before it runs, abort a nested CALL, and — this is the part with no analogue anywhere — turn an ALREADY-SUCCESSFUL transaction into a failed one after the EVM returned, substituting its own return data. Notes 3#

A transaction ordered before it is executed has seven different fates#

Mainnet checks nonce, balance and gas price before a transaction is ordered, so "ordered but invalid" is not a state it can reach. Every chain that separates ordering from execution has to invent an answer, and the rows here have invented seven. There is no portable answer to "was my transaction included".

Erases it. The indexing event is emitted from the last ante decorator, so an ante failure leaves the CometBFT index with no entry while the transaction sits provably in the block.

Full note · Reference · also on Conflux · IOTA EVM · Rollkit · Taraxa · Auto EVM · Bera · RISE · MegaETH · Monad · Hedera

Same consensus engine, opposite failure mode — the Engine API is the discriminator#

Two chains run the same consensus engine, CometBFT, and must answer the same question — what happens to a transaction that is in a proposal but invalid when it executes. They answer oppositely, and the discriminator is not the consensus engine but whether the EVM is inside the ABCI application or behind the Engine API.

The EVM is in-process behind an ante-handler chain, so failure is per-transaction: the transaction is erased, provably in the CometBFT block yet with no index entry and a permanently null receipt.

Full note · Lineage · also on Bera

A failed transaction may spend your nonce and show you nothing#

On mainnet the question cannot arise: an invalid transaction is never included, so the nonce is always preserved and the sender resubmits freely. Where ordering is separated from execution, the nonce may be spent by a transaction that did no work — so "no receipt" does not mean "nothing happened", and the sender cannot tell the two apart from the Ethereum RPC alone.

The dangerous instance. Same shape as the framework, but Artela's PREVRANDAO nil-dereference makes the state reachable from ordinary bytecode rather than from an internal error, and its queryCosmosTxIndexer is stricter still. A sender sees no receipt, concludes nothing happened, resubmits at the same nonce, and is permanently behind a gap no RPC call will reveal.

precompiles0x0000000000000000000000000000000000A27E14 AspectCore
THE ONLY NON-MAINNET PRECOMPILE ON THIS CHAIN, AND IT IS ONLY REACHABLE AS A TOP-LEVEL `to`. Nine ABI-dispatched methods — deploy, upgrade, bind, unbind, changeVersion, versionOf, aspectsOf, boundAddressesOf, entrypoint — implemented in Go with no bytecode in state, so `eth_getCode` returns empty. Solidity-ABI dispatched, like Sei's and the ancestor's and unlike every mainnet precompile. THE INTERCEPTION IS IN THE KEEPER, NOT IN THE EVM. ApplyMessage checks `IsAspectContractAddr(msg.To)` and short-circuits into the native contract BEFORE constructing any call frame. The forked EVM's own precompile lookup (artela-evm/vm/evm.go:precompile) is stock go-ethereum's Berlin map and does NOT contain 0xA27E14. Consequence: a CALL to 0xA27E14 from inside contract bytecode does not reach the Aspect system contract at all — it hits an account with no code, and go-ethereum's Call returns success with empty output. A contract that tries to bind or query an Aspect gets a SILENT NO-OP THAT LOOKS LIKE SUCCESS. This is the inverse of the usual "precompile with no code" hazard: here the address is native at depth 0 and an empty account at depth 1 or more. DEPLOYING AN ASPECT CONSUMES AN EVM ADDRESS. DeployHandler derives the aspect id as `crypto.CreateAddress(from, nonce)` — the same derivation CREATE uses, in the same 20-byte space — and stores WASM there, not EVM code. So the receipt for an Aspect deployment reports a `contractAddress` (ApplyTransaction sets it whenever IsAspectDeploy is true) at which `eth_getCode` will forever return `0x`. Anyone may deploy; deployment is not permissioned.

PREVRANDAO DOES NOT RETURN A WRONG VALUE — IT PANICS THE NODE OUT OF THE TRANSACTION. This is the single sharpest divergence in the row and it is three lines of code. The keeper builds BlockContext with `Random: nil, // not supported`. go-ethereum v1.12.0 derives the merge rule from exactly that field — NewEVM computes chainRules as `chainConfig.Rules(num, blockCtx.Random != nil, time)` — so IsMerge is false. But IsShanghai and IsCancun in v1.12.0 are gated on IsLondon(num) ALONE, so both are true, and the interpreter selects the CANCUN jump table, which is built from the merge set and therefore installs opRandom at 0x44 unconditionally. opRandom then evaluates `interpreter.evm.Context.Random.Bytes()` on a nil *common.Hash, and common.Hash.Bytes has a VALUE receiver — so it dereferences nil. Here 0x44 is an unconditional transaction-killer, and 0x44 is also DIFFICULTY, so pre-merge bytecode is caught by the same trap.

Gotchas 17#

  • YOU CAN BE CHARGED, LOSE YOUR NONCE, AND SEE NO EVIDENCE OF EITHER — AND ORDINARY BYTECODE CAN DO IT TO YOU. The AnteHandler deducts the fee and does `SetSequence(nonce + 1)`, and the SDK commits those writes before the message runs. If execution then fails with anything other than an EVM revert — and executing PREVRANDAO is such a failure, because BlockContext.Random is nil and opRandom dereferences it — the transaction has a non-zero ABCI code, and `TxSuccessOrExceedsBlockGasLimit` erases it from `eth_getBlockByNumber`, from `eth_getTransactionByHash` and from `eth_getTransactionReceipt`. The sender sees a transaction that apparently never existed, resubmits at the same nonce, and is now permanently behind a one-slot gap that nothing but `eth_getTransactionCount` will ever reveal. The ante decorator that emits the index event says in a comment that such a transaction "shouldn't be ignored by json-rpc"; it is ignored anyway.
  • A CONTRACT'S OWNER CAN INSTALL WASM THAT REVERTS OTHER PEOPLE'S TRANSACTIONS, AFTER THEY HAVE ALREADY SUCCEEDED. This is the row's headline. An Aspect is a WASM module bound to a contract; the protocol runs it at four points inside ordinary user transactions. PostContractCall runs after a call frame returned and, if it errors, EVM.Call overwrites both the error AND the return data and reverts to the frame snapshot. PostTxExecute runs only on the SUCCESS path of the whole transaction and, if it errors, overwrites vmErr — so ApplyTransaction never commits and the entire transaction's state is thrown away. Neither involves a REVERT opcode. The transaction that failed was not the Aspect owner's, and the gas was not the Aspect owner's either: join-point execution is metered out of the sender's remaining gas.
  • THE PARTY WHO CAN BIND AN ASPECT IS DECIDED BY ASKING THE CONTRACT. BindHandler calls `isOwner(address)` on the target and, if that call errors, falls back to OpenZeppelin's `owner()`, comparing the answer to msg.sender. So it is the contract's CURRENT owner, not its deployer, and any already-deployed Ownable contract is bindable — including one whose ownership was transferred later. A contract whose `isOwner` returns true unconditionally can be bound by anyone. Nothing asks the contract's users, and nothing in the contract's bytecode or in `eth_getCode` records that an Aspect is attached; the only way to find out is to call `aspectsOf` on the AspectCore precompile.
  • THERE ARE THREE WAYS A TRANSACTION CAN FAIL AND ONLY TWO OF THEM LOOK LIKE FAILURE. AnteHandler rejection during DeliverTx leaves the transaction in the CometBFT block with NO ETHEREUM RECEIPT AT ALL. An EVM revert gives status 0. An Aspect rejection also gives status 0, but with an error string that is not an EVM revert reason and a trace containing no REVERT. A client reading only `receipt.status` cannot tell the last two apart, and a client that trusts `eth_getTransactionReceipt` cannot see the first at all.
  • A TRANSACTION IN A BLOCK CAN HAVE NO RECEIPT, NO `eth_getTransactionByHash` ENTRY, AND NOT APPEAR IN THE BLOCK'S TRANSACTION LIST. The `ethereum_tx` event that carries `ethereumTxHash` is emitted by the LAST ante decorator, so any earlier ante failure — stale nonce, insufficient balance, gas price below the now-current minimum, bad signature — leaves nothing for the CometBFT indexer to find. GetTxByEthHash then errors and GetTransactionReceipt returns null. EthMsgsFromCosmosBlock independently filters the block by TxSuccessOrExceedsBlockGasLimit, so the transaction is missing from `eth_getBlockByNumber` too. THE ONE EXCEPTION IS EXACT AND FRAGILE: a transaction that exceeded the BLOCK gas limit is kept, and it is recognised by a SUBSTRING MATCH on the Cosmos log against the literal "out of gas in location: block gas meter; gasWanted:".
  • EXECUTING PREVRANDAO PANICS THE TRANSACTION OUT OF EXISTENCE. BlockContext.Random is `nil, // not supported`, opRandom calls `.Bytes()` on it, and common.Hash.Bytes has a value receiver — so 0x44 is a nil dereference. The Go panic is caught by the Cosmos SDK's runTx recovery, the resulting log is a Go runtime message rather than the block-gas sentinel, and so the transaction takes the erasure path above: fees deducted and nonce incremented by the ante handler, and nothing at all visible over JSON-RPC. 0x44 is also DIFFICULTY, so pre-merge bytecode hits the same trap. Compare Cosmos EVM, where PREVRANDAO is the constant 0xffff…ff, and Sei, where it is a function of the timestamp.
  • THE CHAIN REPORTS CANCUN AND IS NOT CANCUN. Artela's own Cancun jump table enables EIP-1153 and EIP-5656 and comments out EIP-4844, EIP-7516 and EIP-6780 under a FIXME. So TSTORE and MCOPY work; BLOBHASH and BLOBBASEFEE are UNDEFINED opcodes that burn the frame's gas; SELFDESTRUCT still really destroys; and there is no point-evaluation precompile at 0x0a because the precompile switch stops at Berlin. Four different wrong answers behind one fork name.
  • SHANGHAI AND CANCUN ARE BLOCK NUMBERS HERE. The ChainConfig proto has `shanghai_block` and `cancun_block`, and EthereumConfig() manufactures the ShanghaiTime and CancunTime go-ethereum wants as either 0 or MaxUint64 by comparing the current HEIGHT against them. Ethereum made both of these timestamp forks; Artela un-made that decision. Prague and Osaka have no field at all and are not schedulable.
  • EVERY TRANSACTION IS BILLED FOR AT LEAST HALF ITS GAS LIMIT. ApplyMessage ends with `gasUsed = max(gasLimit * MinGasMultiplier, actualGasUsed)`, default multiplier 0.5, and the receipt reports the floor rather than the measurement. Padding a gas limit — the standard defensive habit everywhere else — is a direct loss, and gas estimators that learn from receipts learn the padded number.
  • A TRANSACTION WITH v = r = s = 0 CAN BE VALID. If the calldata starts with the four bytes 0xCAFECAFE followed by a four-byte keccak checksum, and the target has code, the sender is not recovered — it is RETURNED by a verifier Aspect bound to the target, and accepted if that same Aspect is also bound to the address it named. There is no new transaction type and no envelope change, so every Ethereum tool parses it as an ordinary transaction with a broken signature. `ecrecover(sig) == from` is not false here, it is undefined. Verification costs a flat, non-refundable 150,000 gas added to intrinsic gas.
  • CALLING THE ASPECT SYSTEM CONTRACT FROM A CONTRACT IS A SILENT NO-OP. 0x…A27E14 is intercepted in the keeper by comparing `msg.To`, before any EVM frame is built, and it is NOT in the EVM's own precompile map. So it works as a transaction target and, from inside bytecode, it is an account with no code — which go-ethereum's CALL reports as success with empty output. A contract that tries to bind, unbind or query an Aspect gets a successful-looking call that did nothing.
  • DEPLOYING AN ASPECT MINTS A CONTRACT ADDRESS THAT HAS NO CODE. The aspect id is `crypto.CreateAddress(from, nonce)` — the same derivation CREATE uses, out of the same address space — and the transaction receipt reports it in `contractAddress`. What lives there is WASM in a separate store, so `eth_getCode` at an address a receipt says was just created returns `0x`, forever.
  • A BLOB TRANSACTION IS NOT REJECTED, IT IS DEMOTED. go-ethereum v1.12.0 decodes type 0x03, and Artela's NewTxDataFromTx has cases for only 0x01 and 0x02 with a `default:` that builds a LEGACY transaction — so the type byte, blob hashes and blob fee cap are discarded and the transaction is re-encoded as a 0x00 while MsgEthereumTx.Hash keeps the original 0x03 hash. Because MsgEthereumTx stores the transaction FIELD BY FIELD in a protobuf Any rather than keeping the raw envelope, the original bytes cannot be recovered to check.
  • BLOCKHASH IS NOT LIMITED TO 256 BLOCKS. GetHashFn serves CometBFT header hashes for any height in the current chain epoch out of the keeper's own store, so a contract can read hashes arbitrarily far back. Mainnet contracts that rely on BLOCKHASH returning zero beyond 256 blocks — a common cheap "is this recent" test — silently get a real hash instead.
  • NO MODULE PRECOMPILES AT ALL, WHICH BREAKS PORTS IN THE OPPOSITE DIRECTION. This is a Cosmos EVM chain with no bank, staking, gov, slashing, distribution or IBC precompiles and no bech32 helper — the 0x0100 / 0x0400 / 0x0800-0x0807 block that the cosmos-evm and Sei rows document is entirely empty here. A contract moved from another Cosmos EVM chain does not revert when it calls one; it succeeds with empty output, because those addresses are empty accounts.
  • "ELASTIC EXECUTION" AND PARALLEL EXECUTION ARE NOT IN THE SHIPPED CLIENT. The pinned SDK fork's DeliverTx calls runTx once per transaction against a single deliverState; there is no scheduler, no optimistic execution, no conflict detection and no re-run path anywhere in the five repos. Likewise the Aspect block-level proposal handler exists and is COMMENTED OUT of app.go, so PrepareProposal and ProcessProposal are the stock Cosmos SDK defaults and no Aspect ever runs at the proposal phase.
  • THE NETWORK IS NOT REACHABLE. Every RPC endpoint published for chain id 11820 and 11822 in both chainid.network and chainlist.org, plus artela.network, docs.artela.network and both explorers, returned Cloudflare origin errors or refused connections on 2026-08-27. 2. Aspects: a contract's owner can revert a transaction that already succeeded

The Aspect mechanism is real, it is consensus-level, and it answers the sharp question in the worst direction.

Five join points, a bitmask on the Aspect (aspect-core/types/aspect_type.go): VerifyTx (1), PreTxExecute (2), PreContractCall (4), PostContractCall (8), PostTxExecute (16). The four transaction-level ones fire inside ordinary user transactions, and transactionAdvice looks up the Aspects bound to the contract being called — *msg.To for the transaction-level pair, the frame's addr for the call-level pair. The sender chooses none of it.

What an Aspect can do to a transaction it did not originate:

  • Abort it before it runs. A PreTxExecute error short-circuits ApplyMessage.
  • Abort a nested call and burn the frame's gas. PreContractCall runs inside EVM.Call; on error the call returns that error, and because it is not ErrExecutionReverted, EVM.Call sets gas = 0.
  • Fail a call that already succeeded, and rewrite its return data. PostContractCall runs after interpreter.Run returned. On error: err = postCallResult.Err; ret = postCallResult.Ret, then revert to snapshot.
  • Fail a transaction that already succeeded. PostTxExecute runs only when vmErr == nil — the success path — and its error overwrites vmErr. Back in ApplyTransaction, commit() is called only if !res.Failed(), so the whole transaction's state is discarded.

Who can bind one is the second half of the answer. BindHandler requires, for a target with code, that checkContractOwner return true — and it establishes ownership by calling the target contract: Artela's own isOwner(address) first, and if that call errors, OpenZeppelin's owner(), compared against msg.sender. So the binder is whoever the contract's own code says is its owner: not necessarily the deployer, possibly an address ownership was transferred to afterwards, and — for a contract whose isOwner returns true unconditionally — anyone. The contract's users are never consulted, and nothing in eth_getCode or the bytecode records that an Aspect is attached.

Metering: join-point gas is threaded out of the transaction's own remaining gas. The sender pays for WASM the callee's owner installed. A panic inside the runtime is recovered as "aspect execution crashed" and becomes a revert.

Recorded as system_transactions.aspect_join_points, severity: high.

3. There are three rejection layers, and only two of them look like failure

This is the ordering/execution answer, and it puts Artela in the erasure class alongside Conflux and IOTA EVM — reached by a third mechanism, and with an exact, fragile exception.

Layer 1 — AnteHandler, during DeliverTx: no Ethereum receipt at all. The ethereum_tx event carrying ethereumTxHash is emitted by EthEmitEventDecorator, deliberately the last ante decorator ("emit eth tx hash and index at the very last ante handler"). Any earlier failure — stale nonce, insufficient balance, gas price below the now-current minimum, bad signature — returns from runTx before msCache.Write() and before anteEvents = events.ToABCIEvents(), so neither state nor events survive. The CometBFT indexer therefore has no ethereum_tx.ethereumTxHash entry; GetTxByEthHash errors, and GetTransactionReceipt returns nil, nil → JSON-RPC null. Independently, EthMsgsFromCosmosBlock filters the block through TxSuccessOrExceedsBlockGasLimit, so the transaction is also missing from eth_getBlockByNumber. The transaction is in the CometBFT block and provably so.

The one exception is a substring match. TxExceedBlockGasLimit is strings.Contains(res.Log, "out of gas in location: block gas meter; gasWanted:"). A transaction that busted the block gas limit is kept and surfaced with status: 0. Every other non-zero code is erased.

Layer 2 — EVM revert: ordinary status: 0.

Layer 3 — Aspect: also status: 0, but the error string in res.VmError is the Aspect's own, there is no REVERT opcode anywhere in the trace, and the state rollback happened because commit() was skipped rather than because a snapshot was reverted. A client reading only receipt.status cannot distinguish layers 2 and 3; a client that trusts eth_getTransactionReceipt cannot see layer 1 at all.

4. PREVRANDAO does not return a wrong value — it deletes the transaction

Three lines, in three repos.

  1. x/evm/keeper/evm.go: Random: nil, // not supported.
  2. artela-evm/vm/jump_table.go: newMergeInstructionSet installs opRandom at PREVRANDAO unconditionally, and the Cancun table is built from it.
  3. artela-evm/vm/instructions.go: new(uint256.Int).SetBytes(interpreter.evm.Context.Random.Bytes()).

Context.Random is a *common.Hash, and func (h Hash) Bytes() []byte has a value receiver, so calling it on a nil pointer dereferences nil.

The near-miss worth recording: NewEVM computes chainRules = chainConfig.Rules(num, blockCtx.Random != nil, time), so IsMerge is false — but go-ethereum v1.12.0 gates IsShanghai/IsCancun on IsLondon(num) alone (later versions added the merge gate), so both are true and the interpreter selects the Cancun table anyway. Had this been a slightly later geth, the table would have fallen back to London and 0x44 would have been a harmless DIFFICULTY returning 0. The panic exists because the fork-rule derivation and the jump-table construction disagree about what "merge" means.

The panic unwinds into the SDK's runTx recovery middleware. The resulting log is a Go runtime message, which does not contain the block-gas sentinel — so the transaction takes the layer-1 erasure path of finding 3, except that here the ante handler succeeded: the fee is deducted and the nonce incremented, and nothing at all is visible over JSON-RPC. 0x44 is also DIFFICULTY, so pre-merge bytecode hits it too.

Compare Cosmos EVM (constant 0xffff…ff) and Sei (a function of the timestamp). This is a third answer, and the only one that is not a value.

6. A transaction with v = r = s = 0 is valid, and it wears an ordinary type byte

IsCustomizedVerification returns true when the signature values are nil or all zero, to is non-nil and non-zero, and the calldata begins with the literal four bytes 0xCAFECAFE followed by a four-byte keccak checksum of the remainder. The keeper additionally requires the target to have code.

The rest of the calldata is abi.encode(validationData, callData). The protocol looks up the verifier Aspects bound to the callee, requires exactly one, runs it at the VerifyTx join point, and takes the 20 bytes it returns as the sender — then checks that the claimed sender has itself bound the same Aspect as a verifier. That two-sided opt-in is the only thing between this and arbitrary impersonation.

Consequences: the transaction hash is the hash of an unsigned transaction, so replay protection is whatever the Aspect implements rather than EIP-155; MakeSigner returns an aspectSigner whose SignatureValues() errors; and verification costs a flat, non-refundable 150,000 gas added to intrinsic gas whether it is used or not. The in-source comment claims value transfers must be signed, but the predicate never examines value — the comment is stricter than the code.

There is no new type byte. Every Ethereum tool parses this as an ordinary 0x00 or 0x02 transaction with a broken signature. Recorded as the aspect_verifier scheme, authorizes: account_code — with the note that, unlike zkSync, the validator is not the sender's code but the callee's Aspect.

7. Two Aspect addresses that lie to eth_getCode in opposite ways

0x…A27E14 (AspectCore) is native at depth 0 and empty at depth 1. ApplyMessage intercepts by comparing msg.To against the address before any call frame is built. The forked EVM's own precompile() is stock go-ethereum's Berlin map and does not contain it. So a CALL to 0xA27E14 from inside contract bytecode reaches an account with no code, which go-ethereum's Call reports as success with empty output. A contract that tries to bind, unbind or query an Aspect gets a successful-looking call that did nothing.

Deploying an Aspect mints a contract address with no code. The aspect id is crypto.CreateAddress(ctx.from, ctx.nonce) — the same derivation CREATE uses, out of the same 20-byte space — and ApplyTransaction sets receipt.contractAddress to it whenever IsAspectDeploy holds. The WASM lives in a separate store, so eth_getCode at an address a receipt says was just created returns 0x, permanently. Anyone may deploy; it is not permissioned.

8. Every transaction is billed for at least half its gas limit

ApplyMessage ends with gasUsed = max(gasLimit × MinGasMultiplier, temporaryGasUsed), and DefaultMinGasMultiplier is 0.5. The receipt reports the floor, not the measurement. Padding a gas limit — the standard defensive habit everywhere else — is a direct loss here, and any estimator that learns from receipts learns the padded number. Governance can move the multiplier through x/fee MsgUpdateParams.

9. What Artela is not: three refuted claims

  • No parallel / "elastic" execution. The pinned SDK fork's DeliverTx calls runTx once per transaction against a single deliverState. There is no scheduler, no optimistic execution, no conflict detection and no re-run path in any of the five repos. This is ABCI 0.37 — BeginBlock/DeliverTx/EndBlock/Commit — not ABCI++ 0.38, so there is no FinalizeBlock on this chain at all.
  • No Aspect involvement in block building. app.go constructs an ArtelaProposalHandler and then leaves both SetPrepareProposal and SetProcessProposal commented out. The stock SDK defaults apply: the proposer drains its own mempool in that mempool's order re-running the AnteHandler, and ProcessProposal accepts unconditionally. A proposer may reorder freely and insert its own transactions. The dead handler in x/evm/artela/handle/prepare.go is a verbatim copy of the SDK default with no join point in it.
  • No module precompiles, and no second secp256k1 derivation. There is no precompiles/ package, no ActiveStaticPrecompiles param, and the whole 0x0100/0x0400/0x0800–0x0807 block the cosmos-evm and sei rows document is empty. A contract ported from another Cosmos EVM chain does not revert when it calls one — it succeeds with empty output. Likewise the ancestor's secp256k1_cosmos hazard is absent: Artela's ante switch has cases for ethsecp256k1, ed25519 and multisig only, and its default: rejects everything else.

10. A blob transaction is not rejected, it is demoted

go-ethereum v1.12.0's decodeTyped does handle BlobTxType. Artela's NewTxDataFromTx then switches on the type with cases for only 0x02 and 0x01 and a default: that calls newLegacyTx. So a 0x03 transaction is decoded, stripped of its type byte, blob hashes, blob-gas fee cap and access list, and re-packed as a protobuf LegacyTx, while MsgEthereumTx.Hash keeps the original 0x03 hash. Nothing validates the type anywhere.

This is downstream of an encoding choice: Artela kept Ethermint's old MsgEthereumTx, which stores the transaction field-by-field in a protobuf Any. cosmos/evm v0.7 replaced that with a verbatim raw envelope and reserved 1,2,3,4. On Artela the RLP bytes do not survive, so the original cannot be recovered to check.
