Variation among OP Stack descendants#

OP Mainnet's delta file is empty. Base, on the same stack and client version, reimplements the EVM layer in Rust and adds five fixed precompiles, a dynamic precompile range, native account abstraction (EIP-8130) with its own type byte 0x79, and four chain-specific forks. opBNB carries BSC's precompiles and is pinned three fork generations back. Celo adds type 0x7b (CIP-64, gas paid in an ERC-20), which accounts for 61% of transactions in the blocks sampled. Resolving ethereum → op-stack → X does not determine X's type-byte set.

NOT A SIGNATURE SCHEME. The entry exists because every other row on this axis implies "an accepted transaction has a signer", and on the OP Stack that is false. A 0x7e deposit has no v/r/s — rawSignatureValues returns 0,0,0 — and cannot acquire one: sigHash PANICS with "deposit cannot be signed". The signer short-circuits on the type byte before any cryptography and returns the envelope's own `From` field verbatim, so the sender is READ OUT OF THE TRANSACTION, not recovered from it. This is the one place where the row's `key_binding: derived` does not hold, and `signers_per_tx: 0` is recorded on this path for the same reason. What authorizes it instead is construction by the derivation pipeline, and the client says so in as many words: the txpool rejects every deposit with the comment "No unauthenticated deposits allowed in the transaction pool ... as the external engine-API user authenticates deposits." A deposit can therefore only enter through the authenticated engine API, never the public mempool. For USER deposits op-node scans L1 receipts for the portal's TransactionDeposited logs (UserDeposits) and the portal sets from = msg.sender, aliased by applyL1ToL2Alias when the L1 caller is a contract — so those are ultimately backed by an L1 secp256k1 signature one layer down. But the pipeline also SYNTHESIZES deposits with no L1 event behind them at all: the L1-attributes transaction from 0xdead...0001, and the network-upgrade transactions from 0x4210000000000000000000000000000000000000 and from the ZERO ADDRESS. Nobody holds a key for those senders. Those transactions are authorized by protocol construction and by nothing else. DELIBERATELY NOT the schema's "authorizes: protocol + precompile: none" finding. That finding is about a chain accepting SIGNATURES its own contracts cannot verify. Here there is no signature, so there is nothing a precompile could have been paired with; `precompile: none` records an absence of subject matter, not an unpaired verifier. The integrator hazard is the mirror image and just as sharp: ecrecover over a 0x7e envelope returns garbage rather than failing, because the fields it would read are zero. A second unsigned path exists in the same tree: PostExecTxType 0x7D, whose signer branch returns the ZERO ADDRESS rather than a stored From. Its sigHash also panics. This client contains the type, its marshalling and its receipt handling, but no producer and no fork gate, so whether 0x7D is reachable on any live OP Stack chain is `unrecorded` here.

programmable_eip1271account_codenone
DRAFT (created 2026-03-27), 654 lines, every activation parameter TBD. The name understates it: WIP-1001 reuses EIP-1271's INTERFACE while inverting its semantics. Standard 1271 is a pure predicate over a hash, decided before anything happens. Here authorization is TWO calls that STRADDLE EXECUTION. Step 6 is the familiar one — isValidSignatureForVerifier over a signingHash. Step 12 is not: after the payload has ALREADY RUN tentatively (step 9), the protocol hands the session verifier an ExecutionTraceContext and asks evaluateSessionPolicy whether what just happened was allowed. If it answers false, the tentative state is DISCARDED (step 13). A transaction can be fully executed and then un-executed because a contract disliked the trace. What the verifier sees is not a hash but a WorldChainExecutionTrace: every Call/StaticCall/DelegateCall/Create/Create2 with depth, caller, target, value, selector, input and output hashes, success and gasUsed, plus every log with emitter, topics and callIndex. That is what "programmable" buys — spending limits, MFA on high-value transfers, scoped agent delegation and subscriptions are expressible as policy over observed behaviour, with no protocol branch per scheme. The spec states the principle: no signer-specific authentication as a native execution path. Determinism is enforced, not trusted. Both calls run in restricted validation frames policed by a runtime tracer derived from ERC-7562: 13 rules forbidding block context, tx context, external account inspection, SSTORE/TLOAD/TSTORE, logs, CALL/CREATE and SELFDESTRUCT, permitting STATICCALL only to allowlisted precompiles and DELEGATECALL only to bytecode satisfying the same rules, validated RECURSIVELY (WIP1001-VR-9). A verifier is therefore a pure function of its own storage, its own code, its calldata, and the precompile allowlist. THE CONSEQUENCE FOR THIS AXIS: "Adding a new precompile to the validation allowlist is a hard-fork change." So although authentication is programmable, the set of CRYPTOGRAPHY a verifier can reach is closed by the protocol and widened only by hard fork. This is the direct opposite of zkSync Era, where the equivalent question has no closed answer (see chains/zksync-era) — and a third distinct answer from Base, which enshrines a closed authenticator set in the client with no user code at all. Three designs, three different places to draw the same boundary. Two further protocol-level oddities if it ships. Validation gas is NOT deducted from the envelope gasLimit and is charged instead against a per-block BLOCK_VALIDATION_GAS_BUDGET, so block capacity gains a second dimension and a 0x1D transaction that does not fit is DEFERRED rather than failed. And the failure classes give "failed" two meanings: a payload that REVERTS with an accepted policy is committed as a revert, while a payload the policy REJECTS is discarded — both after burning the nonce and charging a fee. If it ships, this row's key_binding becomes `account_code` for 0x1D and stays `derived` for every other type. Nothing is scheduled: every parameter above is TBD, including EDDSA_PRECOMPILE, whose address WIP-1004 separately proposes to put at 0x0100 where P256VERIFY already lives (see precompiles."0x0100").

Full write-up#

Chain ID 480 · role: fork · upstream: op-stack → ethereum

Reference: worldcoin/world-chain v2.4.2 @ 33281430. Note this repo is a block builder, not an execution client — World Chain runs stock op-reth/op-geth.

The finding is the absence

Every EVM-level fact about World Chain today is inherited from OP Stack unchanged: same opcodes, same precompiles (including all six of OP Stack's semantic divergences from mainnet), same 0x7e deposit type, same three-component fee model, same repurposed blobGasUsed. World Chain adds nothing at the EVM layer.

This is the case the schema was built to represent honestly. A survey that lists "World Chain: World ID, PBH, priority for humans" under EVM differences would be describing marketing. The differences are real but they live somewhere else.

PBH is ordering, not execution

Priority Blockspace for Humans grants verified World ID holders top-of-block priority. Mechanically:

  • It runs through rollup-boost, an external block-production sidecar, "while remaining fully compatible with the OP Stack" (specs/pbh/architecture.md:2).
  • PBH transactions are "standard OP transactions" that call pbhMulticall() or handleAggregatedOps() on PBHEntryPoint with a World ID proof in calldata (specs/pbh/txs.md:3).
  • PBHEntryPoint is an ordinary deployed contract, not a predeploy — no reserved address, no client support required.
  • rollup-boost falls back to the default EL's block if the builder is late or returns an invalid one.

That last point is decisive: a component that can be bypassed by fallback cannot be part of the state transition function. PBH belongs in a block-policy column, not an EVM-difference column.

Everything interesting is in the future tense

crates/chainspec/src/hardfork.rs declares two World-Chain-specific hardforks past the OP sequence — Tropo and Strato. Both are ForkCondition::Never in the shipped spec (asserted at crates/chainspec/src/spec.rs:578-579). Declared, not scheduled. The chain currently defaults to Jovian.

Two allocation problems worth flagging

Tx type 0x1D is on a collision course. Mainnet's typed-envelope allocations grow upward from 0x04 (currently EIP-7702). 0x1D = 29 sits directly in that growth path. Compare OP Stack's 0x7e, deliberately placed at the top of the legal 0x00–0x7f range precisely to avoid this. Draft-stage and cheap to change now.

WIP-1004 places EdDSA at 0x0100 — an address that is already occupied. P256VERIFY lives there on World Chain today, inherited from OP Stack Fjord (RIP-7212) and matching mainnet's EIP-7951. The spec never mentions the overlap, and its rationale (wip-1004.md:105) rests on two premises that were true once and aren't now:

"Reserves a precompile slot above the Ethereum-reserved 0x01–0x0A range and aligns with RIP-7212's convention of placing non-mainnet precompiles starting at 0x0100."

Mainnet has reserved 0x01–0x11 since Prague (EIP-2537 BLS12-381), not 0x01–0x0A. And RIP-7212 occupies 0x0100; it did not open the range above it. WIP-1001's parameter table separately lists BLS12_381_PRECOMPILE as TBD, though BLS12-381 already exists at 0x0b–0x11 on this very chain — the same stale address map showing through twice.

The spec does say the address "MAY be revised by maintainers before activation," so this is a draft to fix, not shipped behaviour. It is recorded because it is exactly the allocation-collision class this dataset exists to surface — and because it shows how fast the "custom precompiles live far from mainnet" convention eroded once 0x0100 itself became a mainnet address at Osaka.

Transaction authorization: World ID does not authorize transactions

This is the axis where World Chain looks most likely to diverge and does not. Execution is stock OP Stack, so secp256k1 is the only scheme that authorizes, key_binding is derived, and 0x7e deposits are unsigned — all of it inherited from op-stack, and the row states no live delta.

The distinction matters because PBH looks like a second authorization scheme. It is not. The semaphore proof travels in the signature field of an ERC-4337 PackedUserOperation, inside a bundle addressed to PBHEntryPoint — an ordinary deployed contract. The builder's pool validator checks the proof only after inner.validate_one has already accepted the transaction as a valid OP transaction, i.e. after ordinary secp256k1 sender recovery has succeeded. The proof buys top-of-block priority, not authority. It does not even reach authorizes: account_code: ERC-4337 is contract-level, so the protocol runs no account validator. And rollup-boost falls back to the default EL's block if the builder returns an invalid one, so the builder cannot make a proof authorize anything the EL would have rejected.

The one genuine proposal on this axis is WIP-1001, and it is a change of kind rather than of curve: a 0x1D envelope executed with a WORLD_CHAIN_ACCOUNT_MANAGER account "framed as the sender", where an immutable EIP-1271 admin signer and a ring of EIP-1271 session verifiers decide what a valid signature is. The spec states the principle outright — no signer-specific authentication as a native execution path — so if it ever ships, World Chain's key_binding becomes account_code for 0x1D and stays derived for everything else. Every activation parameter is still TBD, including the EdDSA precompile address that collides with P256VERIFY. Recorded pending.
