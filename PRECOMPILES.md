## Precompiles that cannot be enumerated

- **Base** — `byte[0] == 0xb2 AND bytes[1..10] == 0 AND byte[10] in {0x00 asset, 0x01 stablecoin}`  
  NOT ENUMERABLE. Beryl installs a PrecompileLookup (BerylLookup) that resolves precompiles by PREDICATE over the address rather than from a fixed map. Every address matching the pattern is a precompile — roughly 2^72 addresses per variant, with the low 9 bytes carrying token identity. No other chain in this dataset has a precompile address space that cannot be listed.
- **Cosmos EVM (evmd)** — `membership is a STATE LOOKUP, not an address predicate: any address present in the x/erc20 native-precompile or dynamic-precompile prefix store is a precompile. For an IBC voucher the address is the last 20 bytes of the denom's sha256 hash (utils.GetIBCDenomAddress), so the set is unpredictable-but-deterministic and can grow at any block.`  
  A SECOND, INDEPENDENT WAY THE PRECOMPILE SET IS NOT ENUMERABLE, and unlike Base's it is not a predicate over the address at all. Base's PrecompileLookup answers a membership question from the address bytes; here the answer lives in module state, so the only way to know whether an address is a precompile is to query the chain at a height. The set grows without governance: an inbound IBC packet carrying an unseen denom registers a new one. AND `eth_getCode` CANNOT TELL YOU. RegisterERC20CodeHash writes a FULL, REAL, COMPILED ERC-20 RUNTIME into state at the precompile's address — x/erc20/types/constants.go:Erc20Bytecode, ~24KB, a genuine OpenZeppelin-style contract — and that bytecode is NEVER EXECUTED, because the call hook installs the native Go precompile for that address first. This is the same trap the Flare and Sonic rows found, one step worse: those chains write a 1-byte stub to satisfy `extcodesize > 0`, so a careful reader still sees something implausible. Here the probe returns a plausible, verifiable, correct-looking ERC-20 that has nothing to do with the code that runs. `eth_getCode == 0x` proves native, but non-empty code proves nothing at all on this framework — the source map is the only sound test.
- **Hedera** — `long-zero address with entity number <= 750 (0x2EE), excluding 0x01-0x0a and 0x167-0x16d`  
  `Version038AddressChecks.isSystemAccount` returns true for EVERY long-zero address whose entity number is <= `NUM_SYSTEM_ACCOUNTS` = 750. In `CustomMessageCallProcessor.start`, such an address that resolves to neither a Besu precompile nor a Hedera system contract reaches `handleNonExtantSystemAccount`, which does `frame.clearGasRemaining()` and then returns `PrecompileContractResult.success(Bytes.EMPTY)`. THE CALL SUCCEEDS, RETURNS NOTHING, AND CONSUMES EVERY UNIT OF GAS FORWARDED TO IT. On mainnet the same call to, say, 0x0b succeeds and costs 100 gas. Here it silently burns the frame's entire gas allowance and the caller sees `success = 1`. Sending VALUE to any such address halts with `INVALID_CONTRACT_ID` instead of creating the account. This also settles the P256VERIFY probe: `eth_call` to 0x0100 returns empty output NOT because EIP-7951 semantics are present but because 0x0100 is inside the sink — Besu 25.2.2's Cancun map has no 0x0100 entry at all.
- **Tempo** — `bytes[0..12] == 0x20C000000000000000000000 (2^64 addresses)`  
  EVERY TIP-20 stablecoin IS A PRECOMPILE, resolved by address prefix through a `set_precompile_lookup` predicate rather than from a map — the second such chain in this dataset after Base's PrecompileLookup, and for a completely different reason. A token created by the TIP20Factory gets an address in this range and its ERC-20 surface is executed as native Rust, not as bytecode. `pathUSD` at 0x20C0..0000 is the canonical one and the default fee token.

## Silent divergences (`severity: high`)

Divergences that produce wrong results with no revert, no error and no signal to the caller — across every section, not just precompiles.

- **BNB Smart Chain** system-contract bytecode — BSC REWRITES system-contract bytecode at fork boundaries via statedb.SetCode. Twenty per-fork bytecode directories exist (bruno, euler, gibbs, moran, planck, plato, luban, kepler, feynman, haber_fix, bohr, pascal, lorentz, maxwell, fermi, pasteur, ...). Unique in this dataset: on every other chain, code at an address changes only by transaction. Here the client swaps it, so the same address can have completely different behaviour across a fork with no on-chain transaction to observe.
- **Polygon PoS `0x0000000000000000000000000000000000001000`** — COLLISION: BSC also uses 0x..1000 for a contract it also calls ValidatorContract. Same address, same name, different chains, different code and ABI — the most confusing possible kind of collision, because the name matches too.
- **Polygon PoS `0x0000000000000000000000000000000000001001`** — COLLISION: BSC uses 0x..1001 for SlashContract. Same address, different purpose.
- **Kaia `0x00000000000000000000000000000000000003fe`** — Returns `contract.FeePayerAddress` — the SECOND SENDER of a fee-delegated transaction, as 20 raw bytes. This is the only way a contract can see who is actually paying, and there is no mainnet equivalent because mainnet has no such party. A contract that authorises on msg.sender alone cannot tell a self-funded call from a sponsored one. Under eth_call, with no transaction and therefore no fee payer, it returns the zero address — verified live.
- **Kaia** header `Extra` — Carries the Istanbul BFT consensus payload — validator addresses, validator seals and the proposer seal. The eth_ namespace REPLACES IT WITH EMPTY BYTES on the way out, with an in-source comment saying the real value "cannot be used as meaningful way". So `extraData` over eth_ RPC is not truncated or encoded differently: it is a lie of omission, and the only way to read the real field is Kaia's own `kaia_` namespace. Confirmed live: extraData is 0x on a block that certainly has consensus data.
- **Sei `0x0000000000000000000000000000000000001004`** — The reconciliation point of the dual address space. getSeiAddr / getEvmAddr resolve one form to the other; associate / associatePubKey create the mapping. Both writers revert under STATICCALL. Before an account is associated, getSeiAddr and getEvmAddr do NOT return zero for it — the keeper's ...OrDefault variants byte-cast the 20-byte address, so an unassociated account silently resolves to a DIFFERENT identity than the one it will have after association. See gotchas.
- **Sei `0x0000000000000000000000000000000000001011`** — RIP-7212 semantics at a NON-STANDARD ADDRESS with a NON-STANDARD CALLING CONVENTION. It is not raw-input: the 160-byte (hash, r, s, x, y) payload must be ABI-encoded as the argument of `verify(bytes)` (selector 0x8e760afe) and the result comes back as ABI-encoded `bytes`. Sending the bare 160 bytes REVERTS. Gas is 300 per input byte of the ABI-encoded call, not a flat 3450 or 6900. DELEGATECALL is refused. A valid signature returns 32 bytes of 0x..01 inside the ABI wrapper; an invalid one returns EMPTY with no error, the same silent-failure shape as EIP-7951. Note the address gap: 0x100d-0x1010 are unallocated, so this is not contiguous with the module block.
- **Sei `0x0000000000000000000000000000000000000100`** — THE COUNTEREXAMPLE. Every other row in this dataset that has a secp256r1 verifier puts it at 0x0100. Sei has one and does not. 0x0100 here is an empty account: EXTCODESIZE 0, a call succeeds and returns empty output. Because EIP-7951 signals "invalid signature" by returning empty output, every P256 verification against 0x0100 on Sei reports invalid forever, silently — identical to the Hyperliquid finding, arrived at by a completely different route (Hyperliquid never implemented it; Sei implemented it somewhere else).
- **Sei** header `stateRoot` — populated with the Tendermint APP HASH, which commits to the entire Cosmos multistore, not to an Ethereum state trie. It is not a Merkle-Patricia root and cannot be used for any Ethereum state proof. Same JSON key, same shape, unrelated meaning.
- **Sei** header `mixHash` — always the zero hash; NOT the PREVRANDAO value the EVM actually saw, which is keccak256(timestamp)
- **Gnosis Chain `0x0B98057eA310F4d31F2a452B414647007d1645d9`** — One contract doing two jobs mainnet splits between a deposit contract and the protocol itself. The chainspec names it as both depositContractAddress and (in the AuRa engine params) withdrawalContractAddress. Withdrawals are executed as a system call into it; deposits are read out of its logs. Mainnet's deposit address is EMPTY here — see eips.6110.
- **Gnosis Chain `0x6BBe78ee9e474842Dbd4AB4987b3CeFE88426A92`** — Where the base fee goes instead of being burned, and from Pectra where the blob base fee goes too. A contract, not a sink — 171 bytes of code at the pinned block. This is the single address that makes "Gnosis burns like Ethereum" false.
- **Gnosis Chain `0x506d1f9efe24f0d47853adca907eb8d89ae03207`** — NOT A PREDEPLOY AND NOT A DEPLOYMENT. This was an externally owned account. The Balancer hard fork (timestamp 1766419900) wrote a fixed HardcodedForwarder bytecode into it during block processing, before the EIP-4788 and EIP-2935 system calls, leaving balance, nonce and storage untouched. The purpose is EIP-3607: an account with code cannot originate transactions, so the attacker's key is neutralised and a named rescue address can forward calls out. VERIFIED END TO END: the live code at this address is byte-identical to BALANCER_RESCUE_BYTECODE in gnosischain/specs AND to the rewriteBytecodeTimestamp entry in Nethermind's chainspec, all three the same 1828 bytes. This is the dataset's first hard fork whose entire content is an irregular state transition, and Gnosis has done it TWICE — the other is GIP-31 below. The mechanism is a first-class chainspec feature (ContractRewriter, keyed by block number or by timestamp), not a patch, and both clients implement it.
- **Gnosis Chain** header `mixHash / nonce (pre-merge: auRaStep / auRaSignature)` — A FLAVOUR OF HEADER DIVERGENCE THIS DATASET HAS NOT SEEN. Pre-merge Gnosis headers have the SAME ITEM COUNT as mainnet's — 16 after London — but items 14 and 15 are not mixHash and nonce. They are auRaStep and auRaSignature, and their sizes are 4 bytes and 65 bytes where mainnet has 32 and 8. Decoded live at block 20,000,000: item 14 = 0x1391ec5a, item 15 = 65 bytes, item 16 = baseFeePerGas 0x07. Nethermind disambiguates the two layouts by PEEKING whether the next item is exactly 32 bytes long, which is the only signal there is. A positional mainnet decoder does not fail on these headers — it reads an AuRa step as a mixHash and a signature as a nonce and computes a wrong block hash. Worse, the JSON-RPC papers over it: eth_getBlockByNumber reports mixHash 0x00..00 and nonce 0x00..00 for that block and adds auraStep and auraSeal as extra keys, so only the RLP tells the truth. POST-MERGE THE HEADER IS EXACTLY MAINNET'S. The pinned block decodes to 21 items in mainnet Osaka order, parentBeaconBlockRoot and requestsHash included. Gnosis is the row whose header shape CONVERGED; the hazard is entirely historical, and it covers 40 million blocks.
- **Sonic `0xd100ec0000000000000000000000000000000000`** — A PRECOMPILE THAT WRITES ARBITRARY STATE. Five methods: `setBalance(acc,value)` sets any account's balance to any number, `setStorage(acc,key,value)` writes any slot of any contract, `incNonce(acc,diff)` bumps any nonce, and `copyCode` / `swapCode` overwrite or EXCHANGE the bytecode of two accounts. Contract code on Sonic is therefore not immutable at the protocol level. The only guard is `caller != driver.ContractAddress -> revert`; the only self-restraint is that `setBalance` and `incNonce` refuse to touch `tx.origin`. IT ALSO BREAKS THE SCHEMA'S PRECOMPILE/SYSTEM-CONTRACT BOUNDARY, which says a precompile has "no bytecode in state, no EXTCODESIZE". Genesis writes a single `0x00` byte to this address, under the comment "set non-zero code for pre-compiled contracts" — so EXTCODESIZE returns 1 and EXTCODEHASH returns keccak(0x00) rather than the empty-code hash, and every "is there a contract here" probe answers YES, while execution is intercepted by the native handler and the stub is never run. It is both categories at once, and the client says it means to be.
- **Sonic `0x0100`** — IN THE SILENT-P256 CLASS, by a cause of its own. On Hyperliquid 0x0100 is simply empty. On Sei it is empty while the chain HAS P256VERIFY elsewhere. On Sonic it is empty because the chain has not activated Osaka — the feature is written, tested and shipped in the pinned client and switched off. The observable is identical in all three cases and identical to a valid-signature rejection under EIP-7951: empty output, no revert, no error. A passkey wallet deployed here verifies nothing and reports "invalid signature" forever, and will start working on a date nobody has set.
- **Sonic `0xd100a01e00000000000000000000000000000000`** — The bridge between consensus and the EVM, and the ONLY account allowed to call the EvmWriter precompile. Its `updateNetworkRules(bytes diff)` is how forks activate on this chain; `advanceEpochs`, `updateValidatorWeight` and `updateValidatorPubkey` reach back into consensus. Every protocol transaction in a Sonic block is addressed here.
- **Sonic** header `extraData` — REPURPOSED AND CONSENSUS-CRITICAL. Exactly 12 bytes: a big-endian uint32 of the block timestamp's nanosecond part, then a big-endian uint64 of the block's DURATION in nanoseconds. The duration is an input to the next block's base fee (`getBaseFeeForNextBlock`), so `extraData` carries a metering dimension the header has no other field for — the same move as OP Stack repurposing `blobGasUsed` for a DA footprint, and as Taiko's second dimension in `difficulty`. Anything treating extraData as an opaque vanity string is discarding a consensus input.
- **Sonic** header `gasLimit` — not the operative limit; see fee_model.validator gas power allocation
- **Berachain `0x4242424242424242424242424242424242424242`** — Berachain's staking deposit contract, at the address Ethereum uses for its TESTNET deposit contracts (Sepolia, Holesky, Hoodi all use 0x4242..4242) — a mainnet chain occupying a well-known testnet address. Different ABI and a different event from Ethereum's: Deposit(bytes,bytes,uint64,bytes,uint64), topic 0x68af7516...891d46. The EL reads its logs to build EIP-6110 deposit requests from Osaka onward.
- **Berachain `0xD2f19a79b026Fb636A7c300bF5947df113940761`** — An ordinary upgradeable proxy at an ordinary-looking address that the PROTOCOL calls once per block. Its address is a chain-config field, so changing it is a hard fork; its CODE is behind a proxy, so changing what the protocol call does is not. Reward distribution logic is therefore governance-mutable without a client release, and the block is invalid if the call is missing.
- **Flare `0x1000000000000000000000000000000000000002`** — THE LARGEST DIVERGENCE ON THIS CHAIN. After EVERY successful transaction the client calls trigger() (selector 0x7fec8d38) on this address with a gas budget of 100x the block gas limit, charged to nobody. Whatever 32-byte value the call returns is treated as a MINT REQUEST and credited to this contract's balance by a direct AddBalance, capped at 60,000,000 FLR per invocation. If the mint is rejected the daemon's state changes are reverted to a snapshot; if the daemon call errors, the failure is only logged and the user's transaction still succeeds. Its side effects land inside the user's receipt: a probed submission transaction carries six logs emitted by this address that its own call tree never produced.
- **Flare `0x2cA6571Daa15ce734Bbd0Bf27D5C9D16787fc33f`** — NOT a genesis contract — an ordinary deployed contract that the CLIENT knows about by hardcoded address. It is the second prioritised address, and it is where essentially all of Flare's traffic goes: 248 of 290 transactions (86%) in a 40-block window. Prioritisation applies when the selector is one of five hardcoded prefixes, the calldata is <= 4500 bytes, the tx gas limit is <= 3,000,000, and the call returned a non-zero word.
- **OP Stack** header `blobGasUsed` — Repurposed to store the DA footprint. Same field name, same RLP position, same JSON key (`blobGasUsed`) — completely different meaning. An indexer computing blob economics from OP chain headers gets silent garbage rather than an error. This is the single nastiest divergence found so far.
- **Celo `0x00000000000000000000000000000000000000fd`** — A REAL added precompile on OP Stack, which op-stack itself has zero of. It moves native CELO between two accounts so the CELO ERC-20 at 0x471E..a438 can be a token and the gas asset at once. Permissioned: it reverts unless the immediate caller is the CeloToken address (celoPrecompileContext.IsCallerCeloToken), and returns ErrWriteProtection under STATICCALL. Cost is params.CallValueTransferGas; input must be exactly 96 bytes. From Jovian it also warms `from` and `to` into the access list — a gas-observable change to an existing precompile. PLACEMENT HAZARD: 0xfd is INSIDE mainnet's own allocation path. Mainnet has reserved 0x01-0x11 and grows upward; every other chain in this dataset that added a precompile went to 0x0100 or far above (Tron 0x1000001+, Monad 0x1000, Sonic 0xd100ec...). Celo went to 0xfd, three addresses below 0x0100, which mainnet already occupies. It is the closest any chain here has parked a custom precompile to mainnet's frontier.
- **Celo `0x15F344b9E6c3Cb6F0376A36A64928b13F62C6276`** — A CONTRACT, not a precompile — it has bytecode and is CALLable normally. The client reads it at the start of every block to build FeeCurrencyContext (exchange rates + per-currency intrinsic gas), so ordinary contract state is an input to the block's fee rules and to intrinsic gas. Governance can change gas costs and fee validity without a client release or a fork. Note the address here is the MAINNET one from the client; CeloPredeploys.sol names 0x9212Fb..11BF, which is the SEPOLIA directory and is EMPTY on mainnet — the contracts repo and the client disagree, and the client is right.
- **Celo `0xcD437749E43A154C07F3553504c68fBfD56B8778`** — From Cel2, the L2 base fee is credited HERE instead of OP Stack's BaseFeeVault at 0x42..19. Anyone accounting OP chain revenue by reading BaseFeeVault gets zero on Celo with no error. The redirect is the IsCel2 branch of the post-execution fee split in core/state_transition.go.
- **Mantle `0xdEAddEaDdeadDEadDEADDEAddEADDEAddead1111`** — ETH's demotion made concrete. Because MNT is the native asset, bridged ETH is an ordinary ERC-20 living at this address — and the client MUTATES IT WITHOUT RUNNING ITS CODE. mintBVMETH and transferBVMETH compute keccak(pad32(addr) || pad32(0)) for the balanceOf mapping and slot 2 for totalSupply and write them with st.state.SetState directly, then FABRICATE the matching `Transfer(address,address,uint256)` and `Mint(address,uint256)` logs with StateDB.AddLog. The token's own code never executes, so any hook, allowance check, pause flag or transfer-restriction it implements is bypassed on the deposit path. The logs look real and are indistinguishable in a receipt. This is outside the 0x42.. predeploy range.
- **Mantle `0x420000000000000000000000000000000000000F`** — SAME ADDRESS, DIFFERENT SLOT MEANING. Storage slot 0 of the OP GasPriceOracle holds `tokenRatio`, the MNT-per-ETH multiplier, and the client reads it from state on every L1-cost calculation — GetState(GasOracleAddr, TokenRatioSlot) appears in the state transition, the state processor, the txpool validator, the simulator and the preconf checker. It is not config and not a fork constant: it is contract storage, so the fee schedule moves when governance moves it, with no client release and no fork. It was 4789 at the probed block and 4778 (0x12aa) in the receipt of a transaction 0x100 blocks earlier — it moves continuously.
- **Mantle** header `blobGasUsed` — Same repurposing op-stack records at Jovian, but gated on IsMantleArsia and therefore live from a different date. It also does MORE here than the field name suggests: CalcBaseFee meters the 1559 update against max(parent.GasUsed, *parent.BlobGasUsed), so the DA footprint sitting in this field directly drives the base fee.
- **Linea `0x03`** — PRECOMPILE_RIPEMD_BLOCKS = 0 in the mainnet trace-limit file. Any transaction that reaches RIPEMD160 with non-empty input exceeds the module limit on its first block and is returned as TX_MODULE_LINE_COUNT_OVERFLOW, dropped from the pool and cached as permanently invalid. It can never be mined. IT STILL WORKS IN eth_call: probing 0x03 with empty input at block 31744343 returned the correct RIPEMD160 of the empty string. So every simulation-based tool — eth_call, eth_estimateGas, Tenderly-style forks, local test suites — reports success for code that cannot be included in a block. This is the schema's hardest case: the precompile is neither `removed` (it executes) nor `modified` (its semantics are exact). `removed` records the fact that matters on-chain.
- **Linea `0x09`** — PRECOMPILE_BLAKE_EFFECTIVE_CALLS = 0 and PRECOMPILE_BLAKE_ROUNDS = 0. The tracer source states the consequence outright: blakeRounds is listed among the modules whose line counting is deliberately skipped "because blakeEffectiveCall is counted and already rejects all BLAKE calls". Zero calls, not zero rounds — a single BLAKE2F invocation with any argument is unincludable. Same eth_call/inclusion split as 0x03.
- **Linea `0x66355689a9f067eeb9dc9d899E4192676988279C`** — Relocated off the canonical 0x00000961Ef480Eb55e80D19ad83579A64c007002, WHICH IS EMPTY ON LINEA. That is the dangerous half: EIP-7002's contract answers a zero-calldata staticcall with the current request fee, and an EMPTY account answers the same call with success and no data. A withdrawal-request client that hardcodes the canonical address — every one written against mainnet does — reads a fee of zero, succeeds, and submits a request that goes nowhere. No revert, no error. Same failure shape as Hyperliquid's empty 0x0100, arrived at independently.
- **Linea `0xF0e003F0dE2d583Ae28FA8cBF66aa096CdAce3ff`** — Relocated off the canonical 0x0000BBdDc7CE488642fb579F8B00f3a590007251, which is also empty on Linea. Identical failure mode to 0x7002 above.
- **Linea** header `extraData` — Repurposed as a consensus-visible pricing channel: a 32-byte struct (version, fixedGasCost, variableGasCost, ethGasPrice) that every node parses and that drives each node's minimum gas price. On mainnet extraData is free-form vanity bytes with no protocol meaning. This is Linea's exact analogue of OP Stack's blobGasUsed repurposing, on a different field — the second independent instance of the pattern in this dataset.
- **Linea** header `parentBeaconBlockRoot` — present and always zero — see eips.4788
- **Scroll `0x0000000000000000000000000000000000000003`** — Disabled since GENESIS (PrecompiledContractsArchimedes, block 0) and still disabled at Galileo, ten forks later. `ripemd160hashDisabled` keeps ripemd160hash's RequiredGas — so the caller is charged the full RIPEMD160 price and then gets an error, and because the error is not ErrExecutionReverted the CALL consumes ALL forwarded gas. "temporarily" has now held for the chain's entire life. Note the error string still names sha256, which was re-enabled at Bernoulli — the message is stale by two years.
- **Scroll `0x0000000000000000000000000000000000000009`** — Same mechanism and same genesis-to-now lifetime as 0x03. blake2FDisabled.RequiredGas returns 0, so unlike 0x03 the caller is not pre-charged before the failure.
- **Scroll `0x5300000000000000000000000000000000000002`** — NOT OP's oracle, and the difference is the address, not the interface. Scroll's L1 fee oracle answers `l1BaseFee()` (0x519b4bd3), `overhead()` (0x0c18c162), `scalar()` (0xf45e65d8), `getL1Fee(bytes)` (0x49948e0e) and `getL1GasUsed(bytes)` (0xde26c4a1) — OP's GasPriceOracle ABI — from 0x53..02 instead of 0x420000000000000000000000000000000000000F, WHICH IS EMPTY ON SCROLL. So the collision here is the mirror image of the ones this dataset usually records: same interface at a different address, rather than a different interface at the same address. Code written against OP's oracle compiles, the address returns success with no data, and the decoded L1 fee is zero. The bytecode is also not deployed by anyone — the CLIENT writes it. Curie, Feynman and GalileoV2 each call statedb.SetCode with a hard-coded Go byte array and seed new storage slots, so three of Scroll's ten forks exist mainly to upgrade this one contract, and its code is a client constant rather than a deployment artefact.
