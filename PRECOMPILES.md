## Precompiles that cannot be enumerated

- **Base** — `byte[0] == 0xb2 AND bytes[1..10] == 0 AND byte[10] in {0x00 asset, 0x01 stablecoin}`  
  NOT ENUMERABLE. Beryl installs a PrecompileLookup (BerylLookup) that resolves precompiles by PREDICATE over the address rather than from a fixed map. Every address matching the pattern is a precompile — roughly 2^72 addresses per variant, with the low 9 bytes carrying token identity. No other chain in this dataset has a precompile address space that cannot be listed.

## Silent divergences (`severity: high`)

Divergences that produce wrong results with no revert, no error and no signal to the caller — across every section, not just precompiles.

- **BNB Smart Chain** system-contract bytecode — BSC REWRITES system-contract bytecode at fork boundaries via statedb.SetCode. Twenty per-fork bytecode directories exist (bruno, euler, gibbs, moran, planck, plato, luban, kepler, feynman, haber_fix, bohr, pascal, lorentz, maxwell, fermi, pasteur, ...). Unique in this dataset: on every other chain, code at an address changes only by transaction. Here the client swaps it, so the same address can have completely different behaviour across a fork with no on-chain transaction to observe.
- **Polygon PoS `0x0000000000000000000000000000000000001000`** — COLLISION: BSC also uses 0x..1000 for a contract it also calls ValidatorContract. Same address, same name, different chains, different code and ABI — the most confusing possible kind of collision, because the name matches too.
- **Polygon PoS `0x0000000000000000000000000000000000001001`** — COLLISION: BSC uses 0x..1001 for SlashContract. Same address, different purpose.
- **Kaia `0x00000000000000000000000000000000000003fe`** — Returns `contract.FeePayerAddress` — the SECOND SENDER of a fee-delegated transaction, as 20 raw bytes. This is the only way a contract can see who is actually paying, and there is no mainnet equivalent because mainnet has no such party. A contract that authorises on msg.sender alone cannot tell a self-funded call from a sponsored one. Under eth_call, with no transaction and therefore no fee payer, it returns the zero address — verified live.
- **Kaia** header `Extra` — Carries the Istanbul BFT consensus payload — validator addresses, validator seals and the proposer seal. The eth_ namespace REPLACES IT WITH EMPTY BYTES on the way out, with an in-source comment saying the real value "cannot be used as meaningful way". So `extraData` over eth_ RPC is not truncated or encoded differently: it is a lie of omission, and the only way to read the real field is Kaia's own `kaia_` namespace. Confirmed live: extraData is 0x on a block that certainly has consensus data.
- **Sei `0x0000000000000000000000000000000000001004`** — The reconciliation point of the dual address space. getSeiAddr / getEvmAddr resolve one form to the other; associate / associatePubKey create the mapping. Both writers revert under STATICCALL. Before an account is associated, getSeiAddr and getEvmAddr do NOT return zero for it — the keeper's ...OrDefault variants byte-cast the 20-byte address, so an unassociated account silently resolves to a DIFFERENT identity than the one it will have after association. See gotchas.
- **Sei `0x0000000000000000000000000000000000001011`** — RIP-7212 semantics at a NON-STANDARD ADDRESS with a NON-STANDARD CALLING CONVENTION. It is not raw-input: the 160-byte (hash, r, s, x, y) payload must be ABI-encoded as the argument of `verify(bytes)` (selector 0x8e760afe) and the result comes back as ABI-encoded `bytes`. Sending the bare 160 bytes REVERTS. Gas is 300 per input byte of the ABI-encoded call, not a flat 3450 or 6900. DELEGATECALL is refused. A valid signature returns 32 bytes of 0x..01 inside the ABI wrapper; an invalid one returns EMPTY with no error, the same silent-failure shape as EIP-7951. Note the address gap: 0x100d-0x1010 are unallocated, so this is not contiguous with the module block.
- **Sei `0x0000000000000000000000000000000000000100`** — THE COUNTEREXAMPLE. Every other row in this dataset that has a secp256r1 verifier puts it at 0x0100. Sei has one and does not. 0x0100 here is an empty account: EXTCODESIZE 0, a call succeeds and returns empty output. Because EIP-7951 signals "invalid signature" by returning empty output, every P256 verification against 0x0100 on Sei reports invalid forever, silently — identical to the Hyperliquid finding, arrived at by a completely different route (Hyperliquid never implemented it; Sei implemented it somewhere else).
- **Sei** header `stateRoot` — populated with the Tendermint APP HASH, which commits to the entire Cosmos multistore, not to an Ethereum state trie. It is not a Merkle-Patricia root and cannot be used for any Ethereum state proof. Same JSON key, same shape, unrelated meaning.
- **Sei** header `mixHash` — always the zero hash; NOT the PREVRANDAO value the EVM actually saw, which is keccak256(timestamp)
- **Linea `0x03`** — PRECOMPILE_RIPEMD_BLOCKS = 0 in the mainnet trace-limit file. Any transaction that reaches RIPEMD160 with non-empty input exceeds the module limit on its first block and is returned as TX_MODULE_LINE_COUNT_OVERFLOW, dropped from the pool and cached as permanently invalid. It can never be mined. IT STILL WORKS IN eth_call: probing 0x03 with empty input at block 31744343 returned the correct RIPEMD160 of the empty string. So every simulation-based tool — eth_call, eth_estimateGas, Tenderly-style forks, local test suites — reports success for code that cannot be included in a block. This is the schema's hardest case: the precompile is neither `removed` (it executes) nor `modified` (its semantics are exact). `removed` records the fact that matters on-chain.
- **Linea `0x09`** — PRECOMPILE_BLAKE_EFFECTIVE_CALLS = 0 and PRECOMPILE_BLAKE_ROUNDS = 0. The tracer source states the consequence outright: blakeRounds is listed among the modules whose line counting is deliberately skipped "because blakeEffectiveCall is counted and already rejects all BLAKE calls". Zero calls, not zero rounds — a single BLAKE2F invocation with any argument is unincludable. Same eth_call/inclusion split as 0x03.
- **Linea `0x66355689a9f067eeb9dc9d899E4192676988279C`** — Relocated off the canonical 0x00000961Ef480Eb55e80D19ad83579A64c007002, WHICH IS EMPTY ON LINEA. That is the dangerous half: EIP-7002's contract answers a zero-calldata staticcall with the current request fee, and an EMPTY account answers the same call with success and no data. A withdrawal-request client that hardcodes the canonical address — every one written against mainnet does — reads a fee of zero, succeeds, and submits a request that goes nowhere. No revert, no error. Same failure shape as Hyperliquid's empty 0x0100, arrived at independently.
- **Linea `0xF0e003F0dE2d583Ae28FA8cBF66aa096CdAce3ff`** — Relocated off the canonical 0x0000BBdDc7CE488642fb579F8B00f3a590007251, which is also empty on Linea. Identical failure mode to 0x7002 above.
- **Linea** header `extraData` — Repurposed as a consensus-visible pricing channel: a 32-byte struct (version, fixedGasCost, variableGasCost, ethGasPrice) that every node parses and that drives each node's minimum gas price. On mainnet extraData is free-form vanity bytes with no protocol meaning. This is Linea's exact analogue of OP Stack's blobGasUsed repurposing, on a different field — the second independent instance of the pattern in this dataset.
- **Linea** header `parentBeaconBlockRoot` — present and always zero — see eips.4788
- **OP Stack** header `blobGasUsed` — Repurposed to store the DA footprint. Same field name, same RLP position, same JSON key (`blobGasUsed`) — completely different meaning. An indexer computing blob economics from OP chain headers gets silent garbage rather than an error. This is the single nastiest divergence found so far.
- **Celo `0x00000000000000000000000000000000000000fd`** — A REAL added precompile on OP Stack, which op-stack itself has zero of. It moves native CELO between two accounts so the CELO ERC-20 at 0x471E..a438 can be a token and the gas asset at once. Permissioned: it reverts unless the immediate caller is the CeloToken address (celoPrecompileContext.IsCallerCeloToken), and returns ErrWriteProtection under STATICCALL. Cost is params.CallValueTransferGas; input must be exactly 96 bytes. From Jovian it also warms `from` and `to` into the access list — a gas-observable change to an existing precompile. PLACEMENT HAZARD: 0xfd is INSIDE mainnet's own allocation path. Mainnet has reserved 0x01-0x11 and grows upward; every other chain in this dataset that added a precompile went to 0x0100 or far above (Tron 0x1000001+, Flare 0x1000...0002). Celo went to 0xfd, three addresses below 0x0100, which mainnet already occupies. It is the closest any chain here has parked a custom precompile to mainnet's frontier.
- **Celo `0x15F344b9E6c3Cb6F0376A36A64928b13F62C6276`** — A CONTRACT, not a precompile — it has bytecode and is CALLable normally. The client reads it at the start of every block to build FeeCurrencyContext (exchange rates + per-currency intrinsic gas), so ordinary contract state is an input to the block's fee rules and to intrinsic gas. Governance can change gas costs and fee validity without a client release or a fork. Note the address here is the MAINNET one from the client; CeloPredeploys.sol names 0x9212Fb..11BF, which is the SEPOLIA directory and is EMPTY on mainnet — the contracts repo and the client disagree, and the client is right.
- **Celo `0xcD437749E43A154C07F3553504c68fBfD56B8778`** — From Cel2, the L2 base fee is credited HERE instead of OP Stack's BaseFeeVault at 0x42..19. Anyone accounting OP chain revenue by reading BaseFeeVault gets zero on Celo with no error. The redirect is the IsCel2 branch of the post-execution fee split in core/state_transition.go.
- **Tron `0x03`** — Does NOT compute RIPEMD160. The implementation computes SHA256(data), copies the first 20 bytes into a 20-byte buffer, and returns SHA256 of that buffer — no RIPEMD anywhere, despite the class name. Ethereum's actual RIPEMD160 is available at 0x020003 as EthRipemd160. Same address as mainnet, entirely different function, no error signalled.
- **Tron `0x09`** — COLLISION. Mainnet's 0x09 is BLAKE2F (EIP-152). Tron placed its batch signature validator there. Tron's BLAKE2F lives at 0x020009 instead.
- **Tron `0x0a`** — COLLISION. Mainnet's 0x0a is KZG point evaluation (EIP-4844). Tron placed its multisig validator there.
- **Monad `0x0000000000000000000000000000000000001000`** — A 15-method staking system reachable as a PRECOMPILE: addValidator, delegate, undelegate, compound, withdraw, claimRewards, changeCommission, externalReward, plus validator/delegator/valset getters, dispatched by 4-byte selector with a per-method fixed gas cost and a 40000-gas fallback. THREE-WAY ADDRESS COLLISION, and it is worse than the ones already in this dataset. BSC and Polygon both put a `ValidatorContract` at 0x…1000 — as SYSTEM CONTRACTS, with bytecode. Monad puts validator staking at the same address as a PRECOMPILE, with no bytecode at all. EXTCODESIZE(0x1000) returns 0 here and non-zero there, so the standard "is there a contract at this address" probe answers differently on three chains that all have staking logic there. Rejects DELEGATECALL/CALLCODE and any non-zero call flag with EVMC_REJECTED.
- **Monad** header `requestsHash` — always the zero hash, never the empty-request-list hash; see eips.7685
- **Monad** header `gasUsed` — Not the gas consumed by the block. Equal to the sum of the transactions' gas LIMITS, because gas_used per transaction is the limit. Same field, same JSON key, different quantity — and it feeds the base-fee update.
- **Hyperliquid (HyperEVM) `0x0a`** — PRESENT IN DISPATCH, PERMANENTLY NON-FUNCTIONAL. Every call — including a well-formed 192-byte input — returns `Revm precompile error: c-kzg feature is not enabled`. The address is not empty (an empty address would succeed with no output); it resolves to a precompile whose implementation was compiled out of the binary. Mainnet control on the same 192 zero bytes returns a semantic error, `mismatched versioned hash`, proving the mainnet precompile is live and merely rejecting the input. This is the exact `tombstoned` vs `removed` distinction SCHEMA.md draws, arrived at from the outside by behaviour alone — and it is the only tombstone in the dataset caused by a BUILD FLAG rather than a deliberate deprecation. The address is consumed either way.
- **Hyperliquid (HyperEVM) `0x0100`** — ABSENT. The one universal address in this dataset is empty here — see eips.7951 and gotchas. Behaves exactly like the unallocated address 0x0101: empty success, 21000 gas.
- **Hyperliquid (HyperEVM) `0x3333333333333333333333333333333333333333`** — 544 bytes of bytecode. Disassembly of the deployed code shows the WHOLE contract: one selector 0x17938e13, an empty 400-iteration loop (PUSH2 0x0190, pure gas burn), then LOG2 of one event, then return. The selector is keccak "sendRawAction(bytes)" and the log topic 0x8c7f585f..12e3 is keccak "RawAction(address,bytes)" — both recomputed locally and matched exactly against the constants embedded in the bytecode and against live logs on chain. Measured cost agrees with the disassembly: eth_estimateGas gives 47042 against a 21000 baseline, and 400 loop iterations plus a two-topic log is about that. severity: high. THERE IS NO SUCCESS SIGNAL. sendRawAction has no return value and cannot revert on a rejected action, because the EVM side only emits a log — HyperCore interprets it afterwards, asynchronously, outside the EVM. A contract that places an order, cancels one, or moves funds through CoreWriter receives a successful call whether HyperCore accepts or rejects the action. Every EVM-level guarantee stops at the log boundary, and no amount of checking the return value helps because there is none.
- **Hyperliquid (HyperEVM) `0x2222222222222222222222222222222222222222`** — 122 bytes. The disassembly is even smaller than CoreWriter: it REVERTS if calldatasize is nonzero, so it accepts only plain value transfers, and on an empty call it emits LOG2 with topic 0x88a5966d..5874 carrying msg.value as data and msg.sender as an indexed topic. That topic is keccak "Received(address,uint256)", recomputed locally and matched against live logs. Same shape as CoreWriter and the same hazard: sending native HYPE here moves it to HyperCore by log interpretation, with no EVM-level confirmation that the credit occurred, and it is a one-way door for anything sent by mistake. Its account also reports a nonce of 1015323, which no ordinary contract would accumulate — see system_transactions.
- **Hyperliquid (HyperEVM)** header `stateRoot` — ALWAYS THE ZERO HASH. Not merely at the pinned height — zero in all 120 blocks scanned AND at blocks 1, 100, 1,000,000, 10,000,000, 20,000,000, 30,000,000 and 40,000,000. HyperEVM headers commit to no state root at all. Corroborating and independent: eth_getProof is not a supported method on the endpoint, which is exactly what one would expect when there is no state trie to prove against. The consequence is that the header cannot be used to verify any state claim — no light clients, no Merkle state proofs, no trust-minimised bridge that reads HyperEVM state from a header. severity: high because the field is PRESENT and well-formed in the JSON; anything that reads it gets a valid-looking 32-byte value that means nothing, with no error anywhere.
- **Hyperliquid (HyperEVM)** header `timestamp` — NOT STRICTLY INCREASING. A large block carries the SAME timestamp as the small block immediately before it: blocks 43436389 and 43436390 both report 1786980420. Two of 119 transitions in the scanned window were non-increasing, matching exactly the two large blocks it contained. Mainnet requires timestamp[n] > timestamp[n-1]; here consecutive distinct blocks tie. Anything that assumes strict monotonicity — an indexer ordering by timestamp, a contract computing an elapsed-time delta and dividing, a TWAP — sees a zero interval. The docs describe the block numbers as "a unique increasing sequence" and say nothing whatsoever about timestamps.
- **zkSync Era `0x05`** — Operands capped at 32 bytes each by circuit limitations — see eips.7823. Over the cap the emulator sets gasToCharge to MAX_UINT64, so the sub-call runs out of gas and returns 0 rather than reverting. A contract that ignores the CALL return value (the common Solidity low-level pattern) proceeds with an empty result.
- **zkSync Era `0x0100`** — Above the 0xff mask, so unlike 0x01-0x08 it presents as an ordinary contract: non-zero EXTCODESIZE and a real EXTCODEHASH, where mainnet's 0x0100 is codeless. See eips.1052.
