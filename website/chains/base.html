Notes 5#

Type-byte allocation from both ends of the range#

EIP-2718 permits 0x00–0x7f. Mainnet allocates upward from 0x00; other chains allocate downward from the ceiling, and there is no registry between the two frontiers. Current occupancy is computed from the data on the transaction types axis.

Allocates downward from the ceiling at 0x79.

Full note · Transaction types · also on Arbitrum · OP Stack · Polygon · Celo · Kaia · zkSync

Base resolves precompiles by predicate rather than from a map#

From the Beryl upgrade, Base installs a PrecompileLookup that tests an address against a pattern instead of looking it up in a fixed table. Every 0xb2-prefixed address matching the B-20 predicate is a precompile — roughly 2^72 addresses per variant. No address-keyed table can represent this, so the schema records the predicate and the site renders it separately from the grid. Tools that build a fixed precompile set treat these as ordinary accounts, with no error raised.

Full note · Precompiles

Precompile verification and transaction authorization are independent#

Whether a precompile can verify a signature scheme and whether that scheme can authorize a transaction are separate properties. Eleven rows carry P256VERIFY; on almost all of them a P-256 key cannot authorize a transfer, because the precompile is callable by contracts and is not an authentication method for senders. tx_authorization records the two separately.

The sharpest counter-example in the dataset. EIP-8130 enshrines a CLOSED set of authenticators in the client — AuthenticatorDispatch routes a 20-byte selector through a hardcoded chain over four canonical values — so on Base a P-256 or WebAuthn key really can move a wei, and it is the CLIENT verifying the signature, not account code. The same curve that is a contract tool elsewhere is a first-class transaction signer here.

Full note · Cryptography · also on Sei · Kaia · zkSync

Variation among OP Stack descendants#

Resolving ethereum → op-stack → X does not determine X's type-byte set, its precompiles, or even its fork schedule.

On the same stack and the same client version as OP Mainnet, Base reimplements the EVM layer in Rust and adds five fixed precompiles, a dynamic precompile range, native account abstraction (EIP-8130) with its own type byte 0x79, and four chain-specific forks.

Some rows do not fit the schema's axes. Each is recorded explicitly rather than reduced to a zero the schema can hold.

Note

EIP-8130 is the opposite design choice to zkSync's, and the contrast is the point. zkSync makes the account's own code the authentication rule, so the scheme set is open and unbounded. Base ENSHRINES a CLOSED set: sender_auth is authenticator(20) || authenticator_data, and AuthenticatorDispatch routes that 20-byte selector through a hardcoded if-chain over four canonical values, falling through to AuthError::NotCanonical for anything else. There is no path by which a user-deployed contract validates a transaction signature. The crate says so in its own README heading — "Enshrined, not a precompile" — and the four authenticators are native Rust, not EVM calls: the deployed contracts at those addresses exist for ERC-1271 use and the native code must stay byte-identical to them, but the protocol never calls them. So on Base a P-256 key really can move a wei, and authorizes: protocol is the honest value: it is the CLIENT verifying the signature, not account code. That makes Base the sharpest counter-example in the dataset to the usual P256VERIFY story — eleven rows carry the precompile and it is a contract tool on almost all of them; here the same curve is a first-class transaction signer. NOT THE UNPAIRED FINDING. Every scheme here has a verifier a contract can reach: secp256k1 at 0x01, P-256 at 0x0100, and the WebAuthn variant is P-256 ECDSA over a SHA-256 message construction, reproducible from 0x0100 plus 0x02. Base even prices the enshrined authenticators off those precompiles deliberately — Eip8130GasSchedule pins 3,000 for k1 and 6,900 for P-256 to the ECRECOVER and EIP-7951 costs. A clean negative. KEY BINDING SPLITS BY PATH, and declared is recorded because 0x79 is what is new. On 0x00-0x04 and 0x7e it is mainnet's derived. On 0x79 with sender == None it is still derived — sender_auth is a bare 65-byte r||s||v and recover_eoa_sender's result IS the sender. With sender == Some(addr) it is declared: the address is an explicit unsigned field and the resolved actorId is checked against an ActorConfig read out of the AccountConfiguration contract's storage, with scope bits and an expiry. ecrecover(sig) != from on that path. TWO PARTIES, TWO DIFFERENT DIGESTS, as on Kaia — arrived at independently. payer is an optional second account that authorizes over payer_signature_hash, which substitutes the RESOLVED sender into the digest and is domain-separated by its own magic byte (0x7A), so a payer signature cannot be replayed under a different sender. The payer's auth blob takes the same authenticator(20)||data form, so a sponsor may itself be a P-256 or WebAuthn key. Absent a payer, the sender pays and payer_auth is empty. NOT LIVE ON MAINNET YET, and the source says why it might move. Cobalt gates 0x79, and the canonical authenticator addresses are CREATE2 derivations of contract init code the repo's own module docs mark "NOT final" and describe as the current Base Sepolia deployment. Probed at block 50098345: ACCOUNT_CONFIG and all three authenticator contracts return empty code on mainnet. So the P-256 schemes below are pending, not added — a P-256 key cannot sign a Base mainnet transaction today. Because the enshrined dispatch keys on those addresses, a re-pin before Cobalt changes WHICH address means P-256; it will not change that P-256 authorizes. A fifth selector, DELEGATE_AUTHENTICATOR, is deliberately NOT recorded as a scheme: it verifies no signature of its own. It wraps one canonical non-delegate authenticator at depth 1 exactly (nesting is NestedDelegate, an error) and surfaces a delegated-account obligation. It changes WHOSE key counts, not WHAT a key is.

For USER transactions there is NO delta from mainnet. op-geth's signer chain is geth's, recoverPlain is the only recovery path in the tree, and the one OP addition to it — NewIsthmusSigner — differs from geth's Prague signer solely by REMOVING BlobTxType from the accepted set. It changes which envelopes may carry a signature, never how a signature is checked or what an address means. The delta on this axis is the deposit path below: transactions the protocol accepts as authorized while carrying no signature at all.

NOT A SIGNATURE SCHEME. The entry exists because every other row on this axis implies "an accepted transaction has a signer", and on the OP Stack that is false. A 0x7e deposit has no v/r/s — rawSignatureValues returns 0,0,0 — and cannot acquire one: sigHash PANICS with "deposit cannot be signed". The signer short-circuits on the type byte before any cryptography and returns the envelope's own `From` field verbatim, so the sender is READ OUT OF THE TRANSACTION, not recovered from it. This is the one place where the row's `key_binding: derived` does not hold, and `signers_per_tx: 0` is recorded on this path for the same reason. What authorizes it instead is construction by the derivation pipeline, and the client says so in as many words: the txpool rejects every deposit with the comment "No unauthenticated deposits allowed in the transaction pool ... as the external engine-API user authenticates deposits." A deposit can therefore only enter through the authenticated engine API, never the public mempool. For USER deposits op-node scans L1 receipts for the portal's TransactionDeposited logs (UserDeposits) and the portal sets from = msg.sender, aliased by applyL1ToL2Alias when the L1 caller is a contract — so those are ultimately backed by an L1 secp256k1 signature one layer down. But the pipeline also SYNTHESIZES deposits with no L1 event behind them at all: the L1-attributes transaction from 0xdead...0001, and the network-upgrade transactions from 0x4210000000000000000000000000000000000000 and from the ZERO ADDRESS. Nobody holds a key for those senders. Those transactions are authorized by protocol construction and by nothing else. DELIBERATELY NOT the schema's "authorizes: protocol + precompile: none" finding. That finding is about a chain accepting SIGNATURES its own contracts cannot verify. Here there is no signature, so there is nothing a precompile could have been paired with; `precompile: none` records an absence of subject matter, not an unpaired verifier. The integrator hazard is the mirror image and just as sharp: ecrecover over a 0x7e envelope returns garbage rather than failing, because the fields it would read are zero. A second unsigned path exists in the same tree: PostExecTxType 0x7D, whose signer branch returns the ZERO ADDRESS rather than a stored From. Its sigHash also panics. This client contains the type, its marshalling and its receipt handling, but no producer and no fork gate, so whether 0x7D is reachable on any live OP Stack chain is `unrecorded` here.

Gotchas 5#

  • BASE PRECOMPILES ARE NOT ENUMERABLE. From Beryl, a lookup predicate makes every 0xb2-prefixed address matching the B-20 pattern a precompile. Any tool that builds a fixed precompile address set — decompiler, tracer, static analyser, or this dataset's own PRECOMPILES.md — is structurally unable to represent Base.
  • Base implements native account abstraction (EIP-8130) as an ENSHRINED feature, not a precompile, with its own transaction type 0x79, 2D nonces and a sender/payer split. It supports EIP-7702 as well, so two distinct AA mechanisms coexist.
  • Base uses its own chain ID as a precompile address prefix (0x8453..). Cute, and collision-free by construction, but only if every chain does it.
  • Base is absent from the superchain-registry mainnet configs, so its fork timestamps are not obtainable the way OP Mainnet's and World Chain's are.
  • The obvious repo (base/node) is Docker packaging only. The real client is base/base. Reading the obvious one produces a confidently empty, wrong row.

Full write-up#

Chain ID 8453 · role: fork · upstream: op-stack · baseline: Osaka

Reference: base/base v1.2.0 @ 8e28af24 — a reth/op-reth-based client in Rust.

First: the repo trap

base/node (68k stars, "Everything required to run your own Base node") is Docker packaging only. It contains a versions.env pointing at the real client, base/base. Reading the obvious repo would have produced a confidently empty row asserting Base has no EVM divergence. It has more than any other OP-Stack descendant here.

Base precompiles are not enumerable

This is the finding that breaks the dataset's own model. At the Beryl upgrade, Base installs a PrecompileLookup (crates/common/precompiles/src/lookup.rs) that resolves precompiles by predicate over the address, not from a fixed map:

pub fn from_address(address: Address) -> Option<Self> {
    let bytes = address.as_slice();
    if bytes[0] != 0xb2 || bytes[1..10] != [0u8; 9] { return None; }
    Self::from_discriminant(bytes[10])       // 0 = Asset, 1 = Stablecoin
}

Any address matching 0xb2 + nine zero bytes + a valid variant byte is a precompile — roughly 2^72 addresses per variant, with the low bytes carrying token identity. These are the B-20 native token precompiles.

Every other chain in this dataset has a precompile set you can list. Base has one you can only test membership in. PRECOMPILES.md is an address-keyed table and is structurally incapable of representing this; the row records a dynamic_range entry with the predicate instead of pretending to enumerate. The same class of problem as Arbitrum's Stylus: a chain diverging along an axis the schema has no column for.

Decompilers, tracers and static analysers that build a fixed precompile set are all wrong on Base, and wrong silently — an unknown address looks like an ordinary account.

Five fixed precompiles, chain-ID-prefixed

Address Name
0x8453…0001 Activation
0x8453…0002 Policy
0x8130…aa01 Nonce (2D nonces for EIP-8130)
0x8130…aa02 TxContext
0xB20F…0000 B20Factory

Base uses its own chain ID (8453) as the address prefix — a placement convention no other chain here uses. Collision-free by construction, but only if everyone adopts it, and BSC/Arbitrum/opBNB demonstrate that nobody has.

Native account abstraction, enshrined

crates/execution/eip8130/ implements EIP-8130, "Account Abstraction by Account Configuration". Its README is explicit: "Enshrined, not a precompile." It brings 2D nonces, a sender/payer split, an intrinsic gas schedule (Eip8130GasSchedule), stateful actor authorization and config-change authorization — gated behind the Cobalt upgrade.

It has its own transaction type: 0x79 (EIP8130_TX_TYPE_ID = 121).

Base also supports EIP-7702, so two distinct account-abstraction mechanisms coexist on the same chain, with two different transaction types.

…and it is a CLOSED set, which is the interesting part

sender_auth is authenticator(20) || authenticator_data, and AuthenticatorDispatch routes that 20-byte selector through a hardcoded if-chain over four canonical values, falling through to AuthError::NotCanonical for anything else:

selector scheme verified by
address(1) (K1_AUTHENTICATOR) secp256k1 native ecrecover — no deployed contract exists
0x28096E…f503 secp256r1, raw native Rust
0xD9B8d1…D7ed secp256r1 under a WebAuthn envelope (a passkey) native Rust
0xb1f064…2a11 not a scheme — 1-hop delegation over one of the above —

There is no path by which a user-deployed contract validates a transaction signature. That is the exact opposite of zkSync, where the account's own code is the authentication rule and the scheme set is open and unbounded. Base's is enshrined and finite.

So on Base a P-256 key can move a wei. Eleven rows in this dataset carry P256VERIFY and on almost all of them the precompile is a tool for contracts and a P-256 key cannot sign anything; here the same curve is a first-class transaction signer, verified by the client. Base is the sharpest counter-example to that pattern. Base even prices the enshrined authenticators off those precompiles deliberately — Eip8130GasSchedule pins 3,000 for k1 and 6,900 for P-256 to the ECRECOVER and EIP-7951 costs.

Not the unpaired finding, and that is a real result: every scheme here has a verifier a contract can reach (0x01, 0x0100, and the WebAuthn construction reassembled from 0x0100 + 0x02).

Two parties, two different digests — the same shape Kaia arrived at independently. payer is an optional second account authorizing over payer_signature_hash, which substitutes the resolved sender into the digest and is domain-separated by its own magic byte (0x7A), so a payer signature cannot be replayed under a different sender. The payer's blob takes the same authenticator(20) || data form, so a sponsor may itself be a passkey.

Not live on mainnet yet. Probed at block 50098345: ACCOUNT_CONFIG and all three authenticator contracts return empty code on Base mainnet, and the repo's own module docs mark those CREATE2 addresses "NOT final", describing them as the current Base Sepolia deployment. The P-256 schemes are therefore recorded pending, not added. A re-pin before Cobalt changes which address means P-256; it will not change that P-256 authorizes.

Its own fork line

Beyond the OP Stack sequence (Bedrock → Jovian), Base has Azul, Beryl, Cobalt, Zombie. Beryl installs the dynamic precompile lookup; Cobalt gates EIP-8130.

Base is absent from the superchain-registry mainnet configs in this snapshot — unlike OP Mainnet and World Chain, whose activation timestamps are published there. So fork order is verified from the BaseUpgrade enum, but timestamps are runtime configuration and are not recorded rather than guessed.

Contrast with OP Mainnet

Same upstream, same OP Stack, and OP Mainnet's delta file is empty. Base reimplements the EVM layer in Rust, adds five fixed precompiles plus an unbounded dynamic range, native AA with its own tx type, and four bespoke forks. "Runs the OP Stack" constrains a chain far less than it sounds like it does.
