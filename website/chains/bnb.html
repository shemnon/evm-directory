Notes 5#

Address collisions at 0x64–0x69 and 0x…1000#

Unrelated chains have independently claimed the same precompile addresses, so a single global address-keyed map is incorrect for at least one major chain whichever way it is populated.

BSC's cross-chain and consensus precompiles occupy 0x64–0x69, the same six addresses Arbitrum uses for its Arb* precompiles; 0x66 and 0x67 are opBNB's too, making those two three-way. BSC also places a ValidatorContract at 0x…1000, a name and address it shares with Polygon's, with different code and a different ABI.

Full note · Precompiles · also on Arbitrum · opBNB · Polygon

0x0100 across the dataset#

Eleven rows carry P256VERIFY at 0x0100, reached through five unrelated forks. Presence at this address indicates neither shared lineage nor a particular fork level, and absence from it does not mean the chain cannot verify P-256.

Carries P256VERIFY at 0x0100 with mainnet semantics and mainnet gas, but reaches it at its own Osaka — five months after mainnet activated the fork of that name.

Fork names and EIP sets diverge in both directions#

Fork names are recorded as claims; the eips: map is the measurement. The two diverge in both directions.

BSC activated Prague seven weeks BEFORE mainnet and Osaka five months AFTER — the same two names, on both sides of mainnet's own dates.

Full note · EIP activation set · also on Avax C · OP Stack

Opcode placement and semantic fidelity vary independently#

Where a chain puts its custom opcodes and precompiles, and how faithful the semantics at mainnet's own addresses are, vary independently.

The most mainnet-faithful EVM here placed its custom precompiles at 0x64–0x69, leaving 0x12–0x63 as headroom before mainnet's upward allocation reaches them.

Full note · Opcodes · also on Tron

Tombstoned precompile addresses#

A tombstoned address is kept alive as an always-reverting stub rather than removed, so it is permanently consumed — and it fails differently from an absent one, which returns success with empty output. Two chains adopted the pattern independently.

BSC tombstoned 0x64 and 0x65 at Pasteur rather than removing them.

Full note · Precompiles · also on Avax C

Transaction authorization#

Key bindingderived
Signers per tx1
Note

UNCHANGED FROM MAINNET for anything a user can send. types.Sender is stock geth, secp256k1 is the only scheme that authorizes a transaction, and the address is still the hash of the recovered public key. Two BSC features look like alternatives and are not. Parlia's fast-finality VOTES are BLS12-381 signatures over block attestations aggregated into the header — that is CONSENSUS signing and cannot move a wei out of an account. blsSignatureVerify at 0x66 is a verifier for CONTRACTS, in exactly the sense P256VERIFY is. Neither is a way to authorize a BSC transaction. Parlia's SYSTEM TRANSACTIONS deserve precision, because BSC is on the opposite side of the line from OP Stack. They are NOT unsigned: applyTransaction builds an ordinary legacy transaction and the block proposer signs it with its normal secp256k1 validator key (signTxFn), so the sender is recovered by the same path as any user transaction. What is special-cased is the RECOVERED ADDRESS, not the signature — IsSystemTransaction accepts one only if the recovered sender equals header.Coinbase, the effective gas price is zero, and the destination is a system contract. Compare OP Stack's 0x7e deposits, which carry no signature at all.

Gotchas 6#

  • BSC shipped Prague SEVEN WEEKS BEFORE Ethereum mainnet (2025-03-20 vs 2025-05-07) and Osaka nearly five months AFTER (2026-04-28 vs 2025-12-03). "Behind mainnet" is not a stable property of a chain — it flips fork to fork.
  • BSC took Prague's EVM half (BLS12-381, EIP-7702, EIP-2935) and dropped its beacon half (4788, 6110, 7002, 7251) via an explicit IsInBSC() early return. A fork-name-only survey would record "Prague" and be wrong about four EIPs.
  • Custom precompiles at 0x64-0x69 leave only 0x12-0x63 of headroom before mainnet grows into them. This is the placement risk flagged from the Ethereum baseline, realised.
  • System contract bytecode is REPLACED BY THE CLIENT at fork boundaries (statedb.SetCode). Code at a fixed address can change with no transaction in any block. Indexers reconstructing contract history from transactions will miss it.
  • 0x64 and 0x65 become always-erroring at Pasteur (activation_time 1787625000 = 2026-08-25) — the same tombstoning pattern as Avalanche's native-asset precompiles.
  • Only chain here with EIP-7702 besides mainnet, and the only one with zero transaction-type divergence.

BPO1Time and BPO2Time are nil with the comment "will be skipped in BSC" — the blob-parameter forks are explicitly declined.

The most mainnet-faithful EVM here

Everything at 0x01–0x11 and 0x0100 matches mainnet Osaka exactly, down to the feature flags:

  • bigModExp{eip2565: true, eip7823: true, eip7883: true} — identical to mainnet
  • p256Verify{eip7951: true} — mainnet gas, unlike OP Stack's 3450
  • Transaction types 0x00–0x04, including EIP-7702 — zero tx-type divergence, the only chain here that can say that

BSC and mainnet are the only two chains in this dataset with EIP-7702.

Client-rewritten system contract bytecode

BSC has 17 system contracts at 0x…1000–1008, 0x…2000–2006, 0x…3000 (validator set, slashing, cross-chain, staking, governance, timelock).

The mechanism is the interesting part. TryUpdateBuildInSystemContract (core/systemcontracts/upgrade.go:1111-1127) calls statedb.SetCode at fork boundaries, and the repo carries twenty per-fork bytecode directories (bruno, euler, gibbs, moran, planck, plato, luban, kepler, feynman, haber_fix, bohr, pascal, lorentz, maxwell, fermi, pasteur, …).

Code at a fixed address changes with no transaction in any block. On every other chain in this dataset, bytecode at an address changes only by transaction. Any indexer reconstructing contract history from transaction traces will silently miss every one of these upgrades. Even EIP-2935's history contract is installed this way (upgrade.go:1117-1120), with the code comment noting it is "a special system contract in bsc, which can't be upgraded".

Block time

450 ms, arrived at by successive halving: 3000 ms default → 1500 ms (Lorentz) → 750 ms (Maxwell) → 450 ms (Fermi) (consensus/parlia/parlia.go:61-64). Consensus is Parlia (Proof of Staked Authority), which inserts system transactions from the block coinbase to system contracts.

What can authorize a transaction: nothing new, and that is the finding

tx_authorization on BSC is deliberately boring — secp256k1, one signer, address = hash of the recovered key, types.Sender unmodified from geth. It is recorded anyway because BSC handles BLS in two places and neither is what it looks like:

  • Parlia fast-finality votes (core/types/vote.go:VoteAttestation) are BLS12-381 signatures over block attestations. They finalise blocks. They cannot move a wei.
  • blsSignatureVerify at 0x66 is a verifier for contracts — the BLS analogue of P256VERIFY at 0x0100, and just as unable to authorize a sender.

There is no BSC transaction envelope that accepts a BLS signature.

Parlia system transactions are signed — unlike OP's deposits

applyTransaction builds an ordinary legacy transaction and the proposer signs it with its normal secp256k1 validator key. What is special-cased is the recovered address, not the signature: IsSystemTransaction accepts one only when the recovered sender equals header.Coinbase, the effective gas price is zero, and the destination is a system contract. BSC and Monad sit on this side of the line; OP Stack's 0x7e deposits, which carry no signature at all, sit on the other.
