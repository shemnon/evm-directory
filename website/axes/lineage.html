Notes 1#

Variation among OP Stack descendants#

OP Mainnet's delta file is empty. Base, on the same stack and client version, reimplements the EVM layer in Rust and adds five fixed precompiles, a dynamic precompile range, native account abstraction (EIP-8130) with its own type byte 0x79, and four chain-specific forks. opBNB carries BSC's precompiles and is pinned three fork generations back. Celo adds type 0x7b (CIP-64, gas paid in an ERC-20), which accounts for 61% of transactions in the blocks sampled. Resolving ethereum → op-stack → X does not determine X's type-byte set.

Where lineage is not a tree#

BNB Smart Chain—
Full-repo geth fork, closely rebased. Tracks mainnet through OSAKA and has the Amsterdam/BPO scaffolding present. The most mainnet-faithful chain in this dataset at the EVM layer.
Polygon PoS—
Full geth fork. Tracks mainnet through PRAGUE (PragueBlock 73440256); no OsakaBlock is set for mainnet, yet the Chicago precompile set pulls in several Osaka-era precompile changes out of band.
Avalanche C-Chain—
libevm v1.13.15-0.20251016142715. EVM behaviour tracks geth through CANCUN only — see forks.
Kaia—
Kaia has kept pace with mainnet fork-for-fork and is CURRENT: Prague at block 190670000 and Osaka at block 213333000, both already past on mainnet (observed at 224632605). Unusually for this dataset the EVM layer is not behind — the divergence is entirely structural, not generational.
Sei—
sei-protocol/go-ethereum v1.15.7-sei-17, a fork of upstream geth v1.15.7. The fork's newest precompile/rule set is PRAGUE. There is no Osaka branch in the fork's config or precompile switch, so Sei is one full fork generation behind mainnet and cannot reach Osaka semantics by configuration alone.
Linea—
Besu @ 6580da84 (gradle/libs.versions.toml `besuCommit`). Upstream Besu ships Linea mainnet as a BUILT-IN network, so the genesis and fork schedule are in the client itself, not in a Linea-owned file.
Arbitrum One—
nitro pins OffchainLabs/go-ethereum as a git submodule; EVM facts come from there, ArbOS facts from nitro itself. The geth fork carries mainnet precompile sets through Osaka, but which set is ACTIVE is gated on ArbOS version, not timestamps — see forks.
OP Stack—
op-geth v1.101702.2 tracks go-ethereum through Osaka. Header struct is identical to geth v1.17.5 except that op-geth lacks EIP-7928 BlockAccessListHash (an unshipped Amsterdam field) and repurposes BlobGasUsed. Rebase, not divergence.
Base—
OP Stack sequence through Jovian, then Base-specific upgrades
World Chain—
Follows the OP Stack upgrade sequence through Karst, then diverges to its own schedule (crates/chainspec/src/hardfork.rs). Currently defaulted to Jovian.
opBNBBNB
STALE relative to its upstream. This client is op-geth v0.5.10, whose newest OP branch is IsOptimismFjord; the op-stack row pins v1.101702.2 (Jovian/Karst). opBNB therefore has NONE of OP Stack's Granite, Isthmus or Jovian changes.
Celo
celo-v2.2.4 is a rebase of op-geth onto go-ethereum v1.16.9 (version/version.go: Major 1, Minor 16, Patch 9), against op-stack's pinned op-geth v1.101702.2 (geth v1.17.5). The OP fork ladder in this tree stops at JOVIAN: params/config.go declares JovianTime and IsOptimismJovian and has no Karst field, and the embedded superchain-registry schema (superchain/types.go HardForkConfiguration) likewise has no karst_time. Celo therefore has NONE of OP Stack's post-Jovian changes, and cannot express them without a client upgrade. The registry's mainnet entry sets no osaka_time, so Celo's EVM is at PRAGUE (isthmus_time = 1752073200) while the op-stack row's baseline is Osaka — a descendant inheriting its ancestor's past, exactly as SCHEMA.md warns.
