Notes 7#

Address collisions at 0x64–0x69 and 0x…1000#

Arbitrum's ArbSys, ArbInfo, ArbAddressTable, ArbBLS, ArbFunctionTable and ArbosTest occupy 0x64–0x69, the same six addresses BSC uses for its cross-chain and consensus precompiles. The two sets share no code and serve unrelated functions. opBNB occupies 0x66 and 0x67 as well, making those two three-way. Polygon and BSC both place a contract named ValidatorContract at 0x…1000, with different code and different ABIs. A single global address-keyed map is therefore incorrect for at least one major chain whichever way it is populated.

Arbitrum · BNB · opBNB · Polygon

Base resolves precompiles by predicate rather than from a map#

From the Beryl upgrade, Base installs a PrecompileLookup that tests an address against a pattern instead of looking it up in a fixed table. Every 0xb2-prefixed address matching the B-20 predicate is a precompile — roughly 2^72 addresses per variant. No address-keyed table can represent this, so the schema records the predicate and the site renders it separately from the grid. Tools that build a fixed precompile set treat these as ordinary accounts, with no error raised.

Base

OP Stack has zero custom precompile addresses and six divergent precompiles#

The divergences are input caps on BN256 and BLS12-381 — a fault-proof constraint expressed in consensus rules — and P256VERIFY at half mainnet's gas. A comparison that diffs address lists finds no difference here.

OP Stack

Same-address divergence, and every flavour is quieter than enumeration#

An address that exists on two chains can differ in ways no address diff sees. OP Stack caps inputs, so the call reverts. Avalanche omits the feature. Polygon reprices — identical result, up to 22× the gas. Tron replaces: 0x03 returns something that is not RIPEMD160. Taiko and Gnosis add a quieter one: the address is canonical and empty, so the call succeeds with no data and no error — on Taiko for all five Cancun/Prague system contracts, which were never deployed because three forks activated at one timestamp; on Gnosis for Ethereum's own deposit contract. Scroll adds the mirror image: OP's GasPriceOracle ABI at a different address, while OP's own 0x42..0F is an empty account, so OP-derived code reads an L1 fee of zero and reports no error. Polygon zkEVM supplies a detection channel the others lack — disabled precompiles stay in the map and so stay WARM (122 gas) while genuinely absent addresses are COLD (2622), which separates the cases by gas alone.

Proof-system constraints leak into consensus — and they expire#

Four chains, four unrelated mechanisms, one cause. OP Stack caps precompile input size, so the call reverts. Linea budgets prover work per block — RIPEMD_BLOCKS=0, BLAKE_ROUNDS=0 — so those precompiles execute in eth_call and can never be mined. zkSync caps modexp operand width at 32 bytes, 32× tighter than EIP-7823. Scroll disabled 0x03/0x09 outright and capped MODEXP the same way. But Scroll also shows the constraints are not permanent: it lifted the 32-byte MODEXP cap at Galileo (2025-12-16) for EIP-7823's 1024 bytes, lifted its SHA256 and BN256 restrictions earlier, and retired the block-level checker entirely — while keeping the two hash tombstones. Polygon zkEVM runs the arc backwards, disabling MODEXP at forkID 8 and never restoring it. So the claim needs a DATE, not just a chain name, and the leak is visible to eth_call on Scroll and Polygon zkEVM but not on Linea. Taiko is the modern form: prover cost as a metered resource (zk gas) rather than a prohibition.

OP Stack · Linea · zkSync · Scroll · zkEVM · Taiko

Tombstoned precompile addresses#

Avalanche's native-asset trio and BSC's 0x64 and 0x65 (at Pasteur) are kept alive as always-reverting stubs rather than removed. The addresses are permanently consumed. Two chains adopted this pattern independently. A tombstoned address fails differently from an absent one, which returns success with empty output.

Avax C · BNB

eth_getCode cannot tell a precompile from a contract#

SCHEMA.md distinguishes a precompile (native code, no bytecode in state) from a system contract (real bytecode at a fixed address), and the obvious test is eth_getCode: empty means precompile. That test fails on eight rows here, in six different shapes, and it fails in BOTH directions. Avalanche's ApplyPrecompileActivations deliberately writes nonce=1, code=0x01 at its precompiles so Solidity's extcodesize guard passes — so Flare's Warp precompile answers 0x01. Sonic writes a 1-byte 0x00 stub at EvmWriter. Tempo writes 0xef; Arc writes 0x01; both give EXTCODESIZE == 1, indistinguishable by size from a real one-byte contract. Cosmos EVM writes a full ~24KB ERC-20 runtime at its dynamic token precompiles that is never executed and decompiles into the contract it impersonates. Moonbeam breaks it the other way too: PrecompileRegistry.updateAccountCode at 0x0815 writes a 5-byte revert stub into any precompile's account and anyone may call it, so 36 of 47 addresses carry code — including all nine of mainnet's, making EXTCODESIZE(0x01) == 5 — while several genuine precompiles return 0x. Conversely Flare's 0x1000…0001–0007, cited elsewhere as custom precompiles, are ordinary system contracts with real genesis bytecode. Classification has to come from the client's precompile map; a probe can only corroborate it.

Cosmos EVM (evmd) — ERC-20 / WERC-20 token-pair precompiles

membership is a STATE LOOKUP, not an address predicate: any address present in the x/erc20 native-precompile or dynamic-precompile prefix store is a precompile. For an IBC voucher the address is the last 20 bytes of the denom's sha256 hash (utils.GetIBCDenomAddress), so the set is unpredictable-but-deterministic and can grow at any block.

A SECOND, INDEPENDENT WAY THE PRECOMPILE SET IS NOT ENUMERABLE, and unlike Base's it is not a predicate over the address at all. Base's PrecompileLookup answers a membership question from the address bytes; here the answer lives in module state, so the only way to know whether an address is a precompile is to query the chain at a height. The set grows without governance: an inbound IBC packet carrying an unseen denom registers a new one. AND `eth_getCode` CANNOT TELL YOU. RegisterERC20CodeHash writes a FULL, REAL, COMPILED ERC-20 RUNTIME into state at the precompile's address — x/erc20/types/constants.go:Erc20Bytecode, ~24KB, a genuine OpenZeppelin-style contract — and that bytecode is NEVER EXECUTED, because the call hook installs the native Go precompile for that address first. This is the same trap the Flare and Sonic rows found, one step worse: those chains write a 1-byte stub to satisfy `extcodesize > 0`, so a careful reader still sees something implausible. Here the probe returns a plausible, verifiable, correct-looking ERC-20 that has nothing to do with the code that runs. `eth_getCode == 0x` proves native, but non-empty code proves nothing at all on this framework — the source map is the only sound test.

Hedera — system-account sink — every address 0x01..0x2EE with no precompile and no system contract

long-zero address with entity number <= 750 (0x2EE), excluding 0x01-0x0a and 0x167-0x16d

`Version038AddressChecks.isSystemAccount` returns true for EVERY long-zero address whose entity number is <= `NUM_SYSTEM_ACCOUNTS` = 750. In `CustomMessageCallProcessor.start`, such an address that resolves to neither a Besu precompile nor a Hedera system contract reaches `handleNonExtantSystemAccount`, which does `frame.clearGasRemaining()` and then returns `PrecompileContractResult.success(Bytes.EMPTY)`. THE CALL SUCCEEDS, RETURNS NOTHING, AND CONSUMES EVERY UNIT OF GAS FORWARDED TO IT. On mainnet the same call to, say, 0x0b succeeds and costs 100 gas. Here it silently burns the frame's entire gas allowance and the caller sees `success = 1`. Sending VALUE to any such address halts with `INVALID_CONTRACT_ID` instead of creating the account. This also settles the P256VERIFY probe: `eth_call` to 0x0100 returns empty output NOT because EIP-7951 semantics are present but because 0x0100 is inside the sink — Besu 25.2.2's Cancun map has no 0x0100 entry at all.
