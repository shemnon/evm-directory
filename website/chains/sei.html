Notes 5#

0x0100 across the dataset#

Eleven rows carry P256VERIFY at 0x0100, reached through five unrelated forks: mainnet Osaka, OP Stack Fjord/RIP-7212, Avalanche Granite, Tron, and Kaia. Most diverge from mainnet in semantics, gas, or both. Presence at this address therefore indicates neither shared lineage nor a particular fork level.

Cryptography · Ethereum · BNB · Avax C · OP Stack · Tron · Kaia · Sei · Hyperliquid

P-256 verification returns empty output on Hyperliquid and Sei#

On Hyperliquid, 0x0100 is an empty account. On Sei, 0x0100 is also empty even though the chain does implement P256VERIFY — at 0x1011, ABI-dispatched as verify(bytes), where a raw 160-byte call reverts. EIP-7951 signals an invalid signature by returning empty output, which is byte-identical to what a call to an absent precompile returns. Every P256 verification against 0x0100 on either chain therefore reports "invalid" with no revert and no error. Distinguishing the two cases requires a valid signature plus a mainnet control on identical calldata; calling the address and checking for output cannot separate them.

Cryptography · Hyperliquid · Sei

Precompile verification and transaction authorization are independent#

Whether a precompile can verify a signature scheme and whether that scheme can authorize a transaction are separate properties. Eleven rows carry P256VERIFY; on almost all of them a P-256 key cannot authorize a transfer. The precompile is callable by contracts, not an authentication method for senders. tx_authorization records the two separately.

Cryptography · Base · Sei · Kaia · zkSync

Schemes that authorize transactions with no precompile able to verify them#

Three schemes have authorizes: protocol with precompile: none: the chain accepts transaction signatures that its own contracts cannot check, so an on-chain multisig, verifier or recovery contract cannot validate what the protocol accepted. Sei's sr25519 (Schnorrkel over Ristretto255, a curve family that chain's EVM cannot compute) and its Cosmos multisig; and Kaia's role-based keys, which are unpaired for two of their three roles — validateSender hardcodes RoleTransaction, so a query about a fee-payer authorization returns an incorrect answer without reverting. The reverse pairing also occurs: Base's EIP-8130 enshrines a closed set of authenticators in the client, so a P-256 or WebAuthn key can authorize a transaction there.

Cryptography · Sei · Kaia

Transactions outside the EIP-2718 envelope#

Avalanche's atomic import and export transactions (UTXO, Avalanche codec) and all 43 of Tron's protobuf contract types carry no EIP-2718 type byte. Two chains with no shared ancestry required the same non_evm_transactions schema section. An indexer enumerating transactions through the EVM envelope does not see Avalanche's cross-chain value movement.

Forks#

Sei has TWO independent upgrade axes and they do not line up. (1) Ethereum fork level, set by the CancunTime/PragueTime chain-config params, both defaulted to 0 — Sei was born Prague-equivalent and has never run a named Ethereum hard fork on mainnet. (2) Sei's own versioned software upgrades ("v6.0.0", "v6.4.0", ...), which are governance-scheduled Cosmos upgrade handlers and are what actually gates precompile behaviour: each custom precompile carries a per-upgrade version map and the active version is chosen by the height at which that named upgrade completed (x/evm/keeper/keeper.go:GetCustomPrecompilesVersions). "Which fork is Sei on" therefore has no single answer, and the Ethereum-fork answer is not the one that determines precompile semantics.

Transaction types 5#

Sei adds NO new EIP-2718 type bytes, and that is misleading on its own. An Ethereum transaction on Sei is not a top-level object: it is packed into a protobuf MsgEVMTransaction inside a Cosmos SDK transaction, which is what consensus actually orders and what the Tendermint block contains. The Ethereum envelope survives inside MsgEVMTransaction.data as a protobuf-encoded TxData, not as RLP. Anything reading Sei blocks at the consensus layer sees Cosmos transactions; the Ethereum view is reconstructed by evmrpc. See non_evm_transactions.

Note

THE FINDING: sr25519 is authorizes: protocol with precompile: none. Sei has two authorization surfaces, and only one of them is Ethereum's. An Ethereum transaction is secp256k1, recovered and stamped as such with no alternative branch. But the same transaction is a MsgEVMTransaction inside a Cosmos SDK transaction, and every OTHER Cosmos message — bank, staking, gov, wasm — goes through the SDK ante chain instead, where the accepted key set is decided by a single switch in DefaultSigVerificationGasConsumer. That switch admits sr25519 and secp256r1 alongside secp256k1. A bank send authorized by an sr25519 signature moves a balance the EVM reads directly: GetBalance resolves an EVM address to its Cosmos counterpart through GetSeiAddressOrDefault, so for an unassociated account the two are the same 20 bytes byte-cast. Nothing on this chain — not Sei's own 0x1001-0x1011 block, not the geth fork's 0x01-0x11 — can verify an sr25519 signature. A contract, a multisig, or a recovery module on Sei cannot check the very signature that just moved the balance it is looking at. THE STATED LEAD WAS ed25519, AND IT IS REFUTED. ed25519 is registered as an account pubkey type and has a working ZIP-215 verifier in the tree, but the same switch rejects it outright: "ED25519 public keys are unsupported", returned before any verification, with no config or governance parameter guarding it. The ConsumeMultisignatureVerificationGas recursion closes the multisig laundering route. It is worth recording as authorizes: no rather than omitting, because getting it wrong in the other direction is the easy mistake: CometBFT VALIDATOR consensus keys are ed25519 (ToTmProtoPublicKey converts to them and refuses secp256k1, exactly inverting the account rule), and those are consensus signatures, not transaction authorization. The residue is a real hazard anyway — an ed25519 account still has a byte-cast 0x address with an EVM-visible balance it can receive into and can never spend from. key_binding is derived on both surfaces, but by two different derivations: an EVM sender is the keccak of a secp256k1 pubkey, a Cosmos signer is that key type's own Address() (sha256-based for the 25519 families), and the two are bridged by a byte-cast, not by a shared key. Association (AssociateTx, the addr precompile's associate/associatePubKey, and the implicit EVMAddressDecorator path) is secp256k1-only in all four routes — btcec.ParsePubKey and a 0x04-prefix check — so an sr25519 or ed25519 account can never associate and is permanently confined to its cast address. signers_per_tx is 1. x/feegrant lets a granter pay without signing, and x/authz lets a grantee's signature execute a granter's message, but neither adds a second signature over the same transaction; both parties signed separately, through this same gate. Sei explicitly blocks MsgEVMTransaction inside authz (CheckAuthzContainsEvm) while leaving bank/staking/gov/wasm reachable.

Precompiles 14#

THIRTEEN custom addresses, all at 0x1001-0x100c plus 0x1011 — four orders of magnitude above every existing row's custom block (BSC/Arbitrum 0x64-0x69, Polygon/BSC 0x1000, Tron 0x1000001+). The dataset's "0x0100 is the one universal address" observation is broken here in the strongest possible way: Sei has the feature AND does not have it at that address. A second, category-level divergence: these are NOT raw-input precompiles. Every one dispatches on a 4-byte ABI method selector and ABI-encodes its result, i.e. they present as Solidity interfaces implemented in native Go. They are still precompiles by this schema's definition — native code, no bytecode in state, EXTCODESIZE 0 (verified live) — but no mainnet precompile behaves this way, and calling one with a raw payload reverts. Custom precompiles are installed ONLY at addresses the built-in map does not already occupy (core/vm/evm.go:NewEVM checks if _, exists := ...; !exists), so Sei can never shadow or modify a mainnet precompile — which is why every entry here is added or removed and none is modified. Each address additionally carries a per-upgrade version map keyed by Sei's own named software upgrades, so "the precompile at 0x1001" is a family of implementations selected by the height at which a governance upgrade completed, not one fixed contract.

0x1011➕P256VERIFY (secp256r1)
RIP-7212 semantics at a NON-STANDARD ADDRESS with a NON-STANDARD CALLING CONVENTION. It is not raw-input: the 160-byte (hash, r, s, x, y) payload must be ABI-encoded as the argument of `verify(bytes)` (selector 0x8e760afe) and the result comes back as ABI-encoded `bytes`. Sending the bare 160 bytes REVERTS. Gas is 300 per input byte of the ABI-encoded call, not a flat 3450 or 6900. DELEGATECALL is refused. A valid signature returns 32 bytes of 0x..01 inside the ABI wrapper; an invalid one returns EMPTY with no error, the same silent-failure shape as EIP-7951. Note the address gap: 0x100d-0x1010 are unallocated, so this is not contiguous with the module block.

System contracts 0#

None at fixed addresses. Sei has no predeploys. The nearest analogue is the ERC-20/721/1155 "pointer" contracts, which ARE real EVM bytecode installed by the chain rather than by a user deployment — but at addresses derived per asset at registration time, not at a fixed, enumerable address. They are therefore neither a predeploy set nor a dynamic_range predicate.

System transactions#

Sei's protocol-driven state changes are Cosmos BeginBlock/EndBlock module logic, not EVM system calls. The two mainnet system calls Sei's client can perform — EIP-4788 beacon-root write and EIP-2935 parent-hash write — are both gated behind replay/blocktest modes and never run on mainnet.

Gotchas 10#

  • 0x0100 IS EMPTY AND SEI HAS P256VERIFY. It is at 0x1011, behind an ABI method selector `verify(bytes)`, priced at 300 gas per input byte, and it refuses DELEGATECALL. A passkey/WebAuthn wallet ported to Sei that calls 0x0100 with the standard 160-byte payload gets empty output — which EIP-7951 defines as "signature invalid" — so it fails closed, silently, forever. Confirmed live with a known-valid signature at block 226969278.
  • EVERY SEI PRECOMPILE IS ABI-DISPATCHED. Raw-input calls revert. This is a category difference from every mainnet precompile and from every other row in this dataset: you cannot probe a Sei precompile by sending it bytes, and any generic precompile fuzzer or shim will see reverts rather than results.
  • ONE ACCOUNT, TWO ADDRESSES, AND THE EVM ONE CAN CHANGE. A Cosmos account that has never associated resolves to `common.BytesToAddress(seiAddress)` — a raw byte-cast of its bech32 payload, unrelated to its public key. After it associates, it resolves to the real secp256k1-derived EVM address. So msg.sender and tx.origin for the SAME Cosmos account differ before and after association. Native balances are migrated across at association time (MigrateBalance), but ERC-20 balances, allowances and any contract storage keyed by the old cast address are NOT — they are stranded at an address nobody controls. There is no event a contract can react to.
  • A BANK SEND TO A CAST ADDRESS CAN BE REJECTED. CanAddressReceive returns false for an address that is the byte-cast of an EVM address which has already been associated with a different sei address. The same 20 bytes are a valid recipient before association and an invalid one after.
  • PREVRANDAO IS keccak256(BLOCK TIMESTAMP). Predictable by anyone. Contracts ported from mainnet that use it for randomness are exploitable and give no outward sign of being broken.
  • THE BASE FEE IS NOT BURNED. It is paid to the fee collector. Sei's fee market is also not EIP-1559: ±1.89%/-0.39% per block toward a 250k-gas target, clamped to a governance floor and ceiling.
  • BLOB TRANSACTIONS ARE ACCEPTED BY THE CODEC AND REJECTED BY THE ANTE HANDLER. Type 0x03 is listed in AllowedTxTypes and then unconditionally refused. The KZG precompile at 0x0a still works.
  • RECEIPTS WITH type = 0xffffffff EXIST. Cosmos and CosmWasm transactions that emit EVM-shaped logs get a synthetic receipt whose type is math.MaxUint32, outside the legal EIP-2718 range entirely. eth_getLogs returns their logs. An indexer storing receipt type in a uint8 corrupts them.
  • THE ETHEREUM BLOCK IS A FICTION AND stateRoot IS THE WORST FIELD IN IT. It carries the Tendermint app hash — a commitment to the whole Cosmos multistore — under the name and shape of an Ethereum state root. No Ethereum state proof against it can ever verify. mixHash is likewise the zero hash rather than the value PREVRANDAO returned.
  • ADDRESS ASSOCIATION IS ITSELF A FREE, NONCE-LESS, TYPE-LESS TRANSACTION. The AssociateTx carries only a signature; its nonce, gas, value and recipient accessors all panic. Nothing in the Ethereum tooling stack can build, sign, decode, simulate or price one.

Full write-up#

Client: sei-protocol/sei-chain v6.6.1 (43d1152e), Go Companion: sei-protocol/go-ethereum v1.15.7-sei-17 (929fc329) — the EVM itself Chain ID: 1329 (pacific-1) · Baseline: Prague · Live probes: block 226969278

Sei is a Cosmos-SDK chain whose EVM interpreter is a maintained fork of go-ethereum. The interpreter tracks upstream; nothing around it does. role: fork describes only the part of Sei that descends from geth by code.

The headline: 0x0100 is empty and Sei has P256VERIFY

The dataset's standing observation was that 0x0100 is the one address twelve of thirteen rows agree on, and that Hyperliquid — where it is empty — is the exception that makes it interesting. Sei is a stronger counterexample, because it is not a chain that skipped the feature.

  • Sei's secp256r1 verifier is at 0x…1011.
  • The geth fork's precompile switch tops out at PrecompiledContractsPrague. There is no Osaka branch, so 0x0100 is never populated by the built-in map.
  • Custom precompiles are installed only where the built-in map is empty (core/vm/evm.go:NewEVM tests if _, exists := evm.precompiles[addr]; !exists), so Sei structurally cannot place anything at a mainnet address.
  • 0x0100 is therefore an ordinary empty account. Calling it succeeds and returns empty output — which EIP-7951 defines as invalid signature.

Verified live against a known-valid signature (the wycheproof CallP256Verify vector shipped in the Kaia repo's p256Verify.json), because the obvious probe cannot distinguish "invalid" from "absent":

eth_call 0x0000000000000000000000000000000000000100  ->  0x
eth_call 0x0000000000000000000000000000000000001011  ->  0x…0020 0020 …0001

A passkey wallet ported to Sei fails closed, silently, forever — the second independent arrival at the Hyperliquid failure mode, by a completely different route.

Second-order: Sei's precompiles are ABI-dispatched

Not a placement difference — a category difference. Every one of the thirteen custom precompiles dispatches on a 4-byte Solidity method selector and ABI-encodes its result. 0x…1011 implements verify(bytes) (0x8e760afe), so the 160-byte RIP-7212 payload must be wrapped in an ABI bytes argument. Sending the bare 160 bytes reverts. Gas is 300 per input byte, not a flat 3450 or 6900. DELEGATECALL is refused.

They are still precompiles by SCHEMA.md's definition — native Go, no bytecode in state, EXTCODESIZE 0 (verified live) — but no mainnet precompile behaves this way, and no generic precompile prober will get a result out of one.

Two wiring traps found while establishing this:

  • precompiles/setup.go contains two disagreeing lists. InitializePrecompiles (which mutates geth's global maps) omits solo and is only ever called with dryRun=true to harvest ABIs. GetCustomPrecompiles is the live path (app/app.go → Keeper.SetCustomPrecompiles → vm.NewEVM) and has all thirteen. The row cites the live path.
  • Each address carries a per-upgrade version map keyed by Sei's own named software upgrades, selected by the height at which that governance upgrade completed (x/evm/keeper/keeper.go:GetCustomPrecompilesVersions). "The precompile at 0x1001" is a family, not a contract.

The dual address space does change CALLER / ORIGIN

Yes — and worse than expected.

An unassociated Cosmos account's EVM address is common.BytesToAddress(seiAddress): a raw byte-cast of its bech32 payload, unrelated to its public key (x/evm/keeper/address.go:GetEVMAddressOrDefault). After it associates, it resolves to the real secp256k1-derived address. So msg.sender and tx.origin for the same Cosmos account are two different addresses before and after association.

utils/helpers/associate.go:MigrateBalance moves native balances (and the sub-usei "wei" remainder) from the cast address to the sei address at association time. It does not move ERC-20 balances, allowances, or any contract storage keyed on the old cast address. Those are stranded at an address nobody controls, with no event a contract can react to.

The reverse edge also bites: CanAddressReceive returns false for a cast address whose EVM counterpart has already associated — the same 20 bytes are a valid bank recipient before association and an invalid one after.

The other headline: an sr25519 signature can move money the EVM watches

tx_authorization was added to answer one question — what can sign a transaction — and Sei is the row where the answer is not "secp256k1".

An Ethereum transaction on Sei is secp256k1 and nothing else: PreprocessUnpacked recovers from (V, R, S) and unconditionally stamps a secp256k1.PubKey. But that transaction is a MsgEVMTransaction riding inside a Cosmos SDK transaction, and every other Cosmos message — bank, staking, gov, wasm — takes the SDK ante chain instead. There, the accepted key set is decided by one switch, DefaultSigVerificationGasConsumer, which admits secp256k1, sr25519, secp256r1, and multisigs over them.

A bank send authorized by an sr25519 signature moves a balance the EVM reads directly: GetBalance resolves an EVM address to its Cosmos counterpart through GetSeiAddressOrDefault, which for an unassociated account is the same 20 bytes, byte-cast. And nothing on this chain can verify an sr25519 signature — not Sei's own 0x1001–0x1011 block, not the geth fork's 0x01–0x11. Grep both; there is no hit.

That is authorizes: protocol with precompile: none: the protocol authorizes a state change that no contract on the same chain can audit. An on-chain multisig or a recovery module on Sei cannot check the very signature that just moved the balance it is reading.

The ed25519 lead is refuted, and the refutation matters. ed25519 is registered as an account pubkey type and has a working ZIP-215 verifier in the tree — and the same switch rejects it before verifying: "ED25519 public keys are unsupported", with no config or governance parameter guarding it, and the multisig path recurses through the same function so it cannot be laundered in. The ed25519 that is live on Sei is the CometBFT validator consensus key (ToTmProtoPublicKey converts to it and refuses secp256k1 — exactly inverting the account rule). Conflating the two would have produced a false finding.

The residue is a real hazard anyway: an ed25519 account still has a byte-cast 0x… address with an EVM-visible balance it can receive into and never spend from. Association — AssociateTx, the addr precompile's associate / associatePubKey, and the implicit EVMAddressDecorator path — is secp256k1-only in all four routes (btcec.ParsePubKey, plus a 0x04-prefix check), so no 25519-family account can ever escape its cast address.

One more: secp256r1 is a real transaction signer here, admitted by the same switch — one of the few rows in this dataset where that is true. Nominally paired, but not portably: the verifier is at 0x1011, not 0x0100, and it is ABI-dispatched as verify(bytes) with per-byte gas rather than taking RIP-7212's raw 160-byte input.

Other integrator-breaking findings

  • The base fee is not burned. baseFee + tip is credited in full to the fee collector as the coinbase reward, with an in-source comment saying so (core/state_transition.go). Sei's fee market is also not EIP-1559: ±1.89% / −0.39% per block toward a 250k-gas target, clamped between governance floor and ceiling.
  • PREVRANDAO is keccak256(block timestamp). Fully predictable. Contracts using it for randomness are exploitable and show no outward sign.
  • Receipts with type: 0xffffffff exist. Cosmos/CosmWasm transactions emitting EVM-shaped logs get a synthetic receipt whose type is math.MaxUint32 — outside the legal EIP-2718 range by a factor of 2^25. eth_getLogs returns their logs.
  • Blob transactions are registered then refused. 0x03 is in AllowedTxTypes from Cancun on and unconditionally rejected by the ante handler → recorded tombstoned.
  • AssociateTx is a free, nonce-less, type-less state-changing transaction. Its TxType(), GetNonce(), GetGas(), GetValue() and GetTo() all panic.
  • The Ethereum block is a fiction, and stateRoot is the worst field in it. It carries the Tendermint app hash — a commitment to the whole Cosmos multistore — under the name and shape of an Ethereum state root. No Ethereum state proof against it can verify. mixHash is the zero hash, not the value PREVRANDAO returned.
  • SeiSstoreSetGasEIP2200 is a params.ChainConfig field in the fork that overrides the clean-zero→nonzero SSTORE cost in both the EIP-2200 and EIP-2929 gas paths, refunds included. Default 20000 = mainnet. The mechanism has no mainnet analogue; whether pacific-1 runs the default is a live value, not a source fact.

Where the schema strained

  • role. Sei is a code fork of geth in the interpreter only. Everything else — envelope, accounts, fees, blocks, addresses — is a rewrite. fork overstates equivalence; independent would understate the literal shared code. Recorded as fork with a chain.note saying which half it applies to. No new key proposed.
  • header_fields. The section assumes a header exists to diff. Sei's consensus block is a Tendermint block; the Ethereum header is assembled at RPC time and is not hashed, signed or committed to. Recorded under header_fields anyway, with a section note saying so, because an integrator reading those fields cannot tell.
  • system_contracts. Sei's pointer contracts are real EVM bytecode installed by the chain rather than by a user — but at addresses derived per asset at registration time. Neither a predeploy set nor a dynamic_range predicate. Recorded as a note.
  • Two upgrade axes. forks.timeline models one sequence. Sei has two that do not line up: Ethereum fork level (all at genesis) and Sei's own governance-scheduled software upgrades (which are what actually gate precompile semantics). Recorded in forks.note; the timeline shows only the Ethereum axis.

Deliberately not established

Nothing is marked status: unrecorded in this row, but these are not established and are called out rather than guessed:

  • Whether pacific-1 currently runs the default SeiSstoreSetGasEIP2200 (20000). It is a live chain-config value; source gives only the default. Recorded as eips.2200: modified with the uncertainty stated in the note, rather than as inherited (which would assert equivalence) or unrecorded (which would hide that the mechanism exists).
  • The exact usei ↔ EVM-gas conversion multiplier. Established that one exists (sdk.NewInfiniteGasMeterWithMultiplier); the constant lives in sei-cosmos, a vendored subtree, and is not pinned as a separate repo.
