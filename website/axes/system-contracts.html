Bytecode that changes with no transaction#

mutable bytecode

BNB Smart Chain — BSC REWRITES system-contract bytecode at fork boundaries via statedb.SetCode. Twenty per-fork bytecode directories exist (bruno, euler, gibbs, moran, planck, plato, luban, kepler, feynman, haber_fix, bohr, pascal, lorentz, maxwell, fermi, pasteur, ...). Unique in this dataset: on every other chain, code at an address changes only by transaction. Here the client swaps it, so the same address can have completely different behaviour across a fork with no on-chain transaction to observe.

added silent divergence
`eth_getCode` returns `0xfe` — ONE BYTE, the INVALID opcode — and it is a RELAY FABRICATION, not state: `ContractService.getCode` short-circuits on `address === constants.HTS_ADDRESS` and returns `constants.INVALID_EVM_INSTRUCTION` "before consulting nodes". No such byte is stored in consensus state and nothing ever executes it. Every other Hedera system contract returns `0x` from the same method. So `EXTCODESIZE`-style contract detection over RPC says "0x167 is a contract, 0x168 is not", which is true of neither. This is the Taraxa "precompile shadowing bytecode" pattern, except the bytecode does not exist and only one of six addresses has it.

0xaaecERC-4337 v0.6 EntryPoint1 chains
ChainDetail & provenance
Artela➕
added silent divergence
REAL EVM BYTECODE, INSTALLED AT GENESIS, AT A NON-CANONICAL ADDRESS. The chain-setup script writes the compiled EntryPoint runtime to 0x…AAEC with `artelad add-genesis-contract`, and aspect-core hard-codes that same address as the target of every Aspect JIT call. Mainnet's EntryPoint v0.6 lives at 0x5FF1…2789 and is deployed by an ordinary transaction; here the address is different and there is no deployment transaction, no deployer nonce and no receipt. Bundler tooling and 4337 SDKs configured with the canonical address will find an empty account. WHETHER MAINNET'S GENESIS ACTUALLY CONTAINED IT IS UNVERIFIED — init.sh is a local-devnet script, and no node was reachable to check. If the address is empty on a given deployment, the Aspect JIT call in system_transactions.aspect_jit_call becomes a call to a codeless account, which go-ethereum reports as SUCCESS with empty return data, so a failed JIT call is indistinguishable from a successful one.

THE BLOCK BENEFICIARY IS A MULTISIG CONTRACT. Genesis allocates five accounts at 0x…0a11b001-005 whose 172-byte code is the standard Gnosis Safe proxy (masterCopy in slot 0, the `a619486e` masterCopy() short-circuit, then a DELEGATECALL fallback), each carrying eleven storage slots, and four of them hold the entire initial XPL supply (~2.5e27, 2.5e27, 1e27 and 4e27 wei). 0x5ca1ab1eL2 "scalable" state account1 chains
ChainDetail & provenance
zkEVM➕
added silent divergence
A CATEGORY THE SCHEMA DOES NOT HAVE. This address has NO BYTECODE — eth_getCode returns 0x — yet it holds the values that three opcodes read, and the protocol writes it before every block. Slot 0 is the block number, slot 1 is the base of a blockNumber->stateRoot mapping, slot 2 is the timestamp, slot 3 is the block-info root. It is not a precompile (no native code, no dispatch) and not a system contract in this schema's sense (no EVM bytecode). It is a protocol-owned storage account, and it is the mechanism behind the BLOCKHASH and NUMBER divergences below. Recorded here because leaving it out would hide the cause of two silent opcode redefinitions.
