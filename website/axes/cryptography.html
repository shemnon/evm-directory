Notes 5#

0x0100 across the dataset#

Eleven rows carry P256VERIFY at 0x0100, reached through five unrelated forks: mainnet Osaka, OP Stack Fjord/RIP-7212, Avalanche Granite, Tron, and Kaia. Most diverge from mainnet in semantics, gas, or both. Presence at this address therefore indicates neither shared lineage nor a particular fork level.

Ethereum · BNB · Avax C · OP Stack · Tron · Kaia · Sei · Hyperliquid

P-256 verification returns empty output on five chains, for five reasons#

EIP-7951 signals an invalid signature by returning empty output — byte-identical to what a call to an absent precompile returns. On five rows here 0x0100 is empty, so every P-256 verification against it reports "invalid" with no revert and no error, and each row gets there differently. On Hyperliquid the address is simply an empty account. On Sei it is empty even though the chain DOES implement P256VERIFY, at 0x1011, ABI-dispatched as verify(bytes), where a raw 160-byte call reverts. On Sonic the precompile map is Prague's and Osaka never activated. On Injective the fork level cannot reach Osaka at all, overriding the Cosmos EVM framework's entry, which does carry it. On Polygon zkEVM it is implemented as p256Verify_zkevm and present in a forkID that has never activated. A passkey wallet ported to any of them is broken and looks merely strict. Distinguishing the cases requires a valid signature plus a mainnet control on identical calldata; calling the address and checking for output cannot separate them — which is why an address-diff survey reports all five as fine.

Hyperliquid · Sei · Sonic · Injective · zkEVM

Precompile verification and transaction authorization are independent#

Whether a precompile can verify a signature scheme and whether that scheme can authorize a transaction are separate properties. Eleven rows carry P256VERIFY; on almost all of them a P-256 key cannot authorize a transfer. The precompile is callable by contracts, not an authentication method for senders. tx_authorization records the two separately.

Base · Sei · Kaia · zkSync

Schemes that authorize transactions with no precompile able to verify them#

Three schemes have authorizes: protocol with precompile: none: the chain accepts transaction signatures that its own contracts cannot check, so an on-chain multisig, verifier or recovery contract cannot validate what the protocol accepted. Sei's sr25519 (Schnorrkel over Ristretto255, a curve family that chain's EVM cannot compute) and its Cosmos multisig; and Kaia's role-based keys, which are unpaired for two of their three roles — validateSender hardcodes RoleTransaction, so a query about a fee-payer authorization returns an incorrect answer without reverting. The reverse pairing also occurs: Base's EIP-8130 enshrines a closed set of authenticators in the client, so a P-256 or WebAuthn key can authorize a transaction there.

Sei · Kaia

No post-quantum scheme in the dataset#

Across all nineteen rows the signature schemes are secp256k1, secp256r1 (P-256), BLS12-381, BN254, ed25519, sr25519 and SM2 — all discrete-log-based. No row carries ML-DSA, SLH-DSA, Falcon or any other lattice- or hash-based scheme, as a transaction signer, as a precompile, or as status: pending. Recorded explicitly because an empty column is otherwise indistinguishable from an unfinished survey.

Authorizes with no precompile to verify it#

unpaired

Kaia — secp256k1_role_based

UNPAIRED FOR TWO OF ITS THREE ROLES. A RoleBased key holds up to three independent sub-keys — RoleTransaction, RoleAccountUpdate, RoleFeePayer — and Validate selects by index on the role the protocol chose: GetRoleTypeForValidation returns RoleAccountUpdate for the account-update types and RoleTransaction otherwise, while ValidateFeePayer passes RoleFeePayer outright. The validateSender precompile hardcodes RoleTransaction, so a contract can ask "does this satisfy the transaction key" and CANNOT ask "does this satisfy the fee-payer key" or "the account-update key" — the protocol has just answered a question the chain gives bytecode no way to re-ask. Sharpened by the fallback in getDefaultKey: a role left unset silently resolves to RoleTransaction, so whether the gap bites depends on how many sub-keys the account actually registered, which a contract also cannot see through 0x03ff.

unpaired

Sei — sr25519

UNPAIRED. Schnorrkel over Ristretto255 — a different curve family from anything the EVM can compute here. Accepted by the ante chain's key switch (GetSr25519VerifyCost, then `return nil`) and verified by a real curve25519-voi implementation, not a stub. There is no sr25519 verifier at any address on this chain: grep over precompiles/ and the geth fork's core/vm returns nothing. So the protocol will authorize a state change that no contract on the same chain can audit. Two honest limits on this row: the code path is open but whether any sr25519 account exists on pacific-1 is live state and was not probed, and the EVM sees the EFFECT (a balance) rather than the signature, so the gap bites an on-chain verifier rather than ordinary execution.

unpaired

Injective — ed25519

OVERRIDE of the framework's `never`, and the finding of this row. DefaultSigVerificationGasConsumer's ed25519 case consumes SigVerifyCostED25519 and returns nil — accepted, not refused. No precompile on Injective can verify an Ed25519 signature, so a contract, a multisig or a recovery module here cannot check the signature that just moved the balance it is looking at. Two honest limits: the code path is open but no census of live ed25519 accounts on injective-1 was taken, and the EVM observes the EFFECT (a bank balance) rather than the signature.

unpaired

Hedera — ed25519

THE `authorizes: protocol` + `precompile: none` PAIRING SCHEMA.md ASKS FOR. ED25519 is the ORIGINAL and still most common Hedera key type: it can pay for, and authorize, any HAPI transaction including one that carries an EVM call. There is NO ED25519 verification precompile in the Besu Cancun set, so an on-chain multisig, guardian or recovery contract written in Solidity CANNOT verify the very signatures the protocol just accepted. The only in-EVM path to an ED25519 check is `isAuthorizedRaw` on the Hedera Account Service system contract at 0x16a, which is a Hedera-specific dispatch, not a precompile, and which `CustomGasCalculator.getEdSignatureVerificationSystemContractGasCost` prices at the ECRECOVER rate.

unpaired

Sei — multisig

Cosmos LegacyAminoPubKey k-of-n over the schemes above. Recurses through ConsumeMultisignatureVerificationGas, so it inherits the allowlist exactly and cannot launder ed25519 in. Unpaired for the same reason sr25519 is, and additionally because no precompile reproduces the threshold arithmetic — contrast Kaia, which exposes exactly that at 0x03ff. The nearest thing Sei has is the solo precompile at 0x100c, which decodes a whole Cosmos transaction from EVM calldata and runs the SAME verification stack; it is not a scheme verifier and is depth- and delegatecall-restricted, but it is the only bridge of this kind in the dataset and it inherits the same ed25519 rejection.

unpaired

Cosmos EVM (evmd) — multisig

Cosmos LegacyAminoPubKey k-of-n, valid on the Cosmos surface only. Unpaired: no precompile on this framework reproduces the threshold arithmetic, so a contract cannot audit a state change a multisig authorized. Recursion through the same switch means it inherits the ed25519 refusal exactly.

unpaired

Injective — multisig

Cosmos LegacyAminoPubKey, recursing through the same switch — which on Injective means it can now legitimately contain ed25519 members, unlike the framework where the recursion closed that route.

unpaired

Artela — multisig

Cosmos LegacyAminoPubKey k-of-n on the Cosmos surface only; recurses through the same switch, so it inherits both the ed25519 refusal and the rejection of Cosmos-style secp256k1 keys. No precompile reproduces the threshold arithmetic.

unpaired

Berachain — protocol_system_address

The 0x7E PoL transaction is authorized by nothing at all: v, r and s are literal zeros, `from` is the constant 0xfff..ffe, and validity is decided by recomputing the transaction and comparing hashes. This is the OP-deposit pattern (unsigned, protocol-authored) arrived at independently, and it lands on the same type byte. It cannot reach the mempool — the pool rejects PoLTxType outright — so the ONLY way one exists is for a block producer to synthesise it, and the only way it is accepted is for every other node to derive byte-identical bytes from the header.

unpaired

MegaETH — system_address

NOT A SIGNATURE SCHEME — an ADDRESS-KEYED bypass. `is_deposit_like_transaction` returns true for any legacy transaction whose caller equals the current system address, and deposit-like processing skips signature validation entirely. The authorization is therefore "the sequencer put this transaction in the block with this `from` field", exactly as for an OP deposit, except that the envelope is an ordinary legacy transaction rather than the 0x7e type that announces itself. The keyless-deploy sandbox transaction takes the same path under `SANDBOX_TX_SOURCE_HASH`. `precompile: none` here records an absence of subject matter, not an unpaired verifier — there is no signature to verify.

unpaired

Scroll — l1_message_queue

`authorizes: protocol` with `precompile: none` — the pairing SCHEMA.md flags as the finding to look for. The client authorises a 0x7e transaction by reading `tx.AsL1MessageTx().Sender` and returning it; no cryptography runs on L2 at all. An L2 contract handed an L1 message cannot verify that the claimed sender authorised it, because the authorising signature was consumed on Ethereum and never crosses the bridge. The pool refuses to accept the type from the network ("No unauthenticated deposits allowed in the transaction pool"), so the only producer is the sequencer's L1 sync service — which makes sequencer honesty, not a signature, the thing an L2 contract is trusting. Shape-identical to OP Stack's deposit authorization; independently arrived at, on the same type byte.

unpaired

Moonbeam — xcm_origin

THE unpaired one. A message from another parachain can execute an EVM transaction whose sender is an XCM-derived account, and the runtime forges an Ethereum envelope for it: `pallet-ethereum-xcm` builds an `EIP1559Transaction` with r = s = H256::from_low_u64_be(1) — a fixed, deliberately invalid signature — and stores it in the Ethereum block. The result appears over JSON-RPC as an ordinary type-0x02 transaction with a `from`, an `r` and an `s`, and `ecrecover` over it does not yield `from` and never can. No contract on Moonbeam can verify the authorisation behind such a transaction, and no indexer that trusts the signature can tell one from a user transaction except by recognising the constant. `transact_through_proxy` widens it further: the XCM origin may act as any LOCAL account that granted it a zero-delay `ProxyType::Any` proxy, so `msg.sender` becomes a Moonbeam account that signed nothing in this transaction. `force_transact_as` lets Root do the same with no proxy at all.

unpaired

Hedera — key_lists_and_thresholds

A payer's `Key` may be an m-of-n threshold list or an arbitrarily nested key list mixing ED25519 and ECDSA. The protocol validates it; no EVM code can.

unpaired

Hedera — contract_id_keys

A `Key` may BE a contract ID: the "signature" is satisfied when that contract is the active frame. This is account abstraction at the protocol level with no transaction type, no entry point and no EVM representation.

unpaired

Taraxa — system_unsigned

A transaction with r = 0 and s = 0 whose sender is the constant 0x0054617261786153797374656d4163636f756e74 — which is ASCII for \x00 followed by 'TaraxaSystemAccount'. `authorizes: protocol` with `precompile: none` is the pairing SCHEMA.md flags: an on-chain contract has no way to check the authority behind a system transaction, because there is nothing to check.

unpaired

Tempo — webauthn

`authorizes: protocol` WITH `precompile: none` — the finding SCHEMA.md names. The client validates a full WebAuthn assertion (authenticatorData flags, clientDataJSON challenge binding, base64url) to authorize a transaction, and no precompile on this chain performs that composite check. A contract can call P256VERIFY on the inner ECDSA signature but cannot reproduce the authenticator-data and challenge validation the protocol just performed, so an on-chain recovery or multisig contract cannot re-verify a signature its own chain accepted.

unpaired

Tempo — keychain

A wrapper, not a curve: any of the three primitive schemes signed by a key registered in the AccountKeychain precompile at 0xAAAAAAAA00..00, acting for a declared `user_address` under a spending limit. Two versions (0x03 legacy, 0x04 current) differ in the digest. No precompile validates the wrapper itself.

DRAFT (created 2026-03-27), 654 lines, every activation parameter TBD. The name understates it: WIP-1001 reuses EIP-1271's INTERFACE while inverting its semantics. Standard 1271 is a pure predicate over a hash, decided before anything happens. Here authorization is TWO calls that STRADDLE EXECUTION. Step 6 is the familiar one — isValidSignatureForVerifier over a signingHash. Step 12 is not: after the payload has ALREADY RUN tentatively (step 9), the protocol hands the session verifier an ExecutionTraceContext and asks evaluateSessionPolicy whether what just happened was allowed. If it answers false, the tentative state is DISCARDED (step 13). A transaction can be fully executed and then un-executed because a contract disliked the trace. What the verifier sees is not a hash but a WorldChainExecutionTrace: every Call/StaticCall/DelegateCall/Create/Create2 with depth, caller, target, value, selector, input and output hashes, success and gasUsed, plus every log with emitter, topics and callIndex. That is what "programmable" buys — spending limits, MFA on high-value transfers, scoped agent delegation and subscriptions are expressible as policy over observed behaviour, with no protocol branch per scheme. The spec states the principle: no signer-specific authentication as a native execution path. Determinism is enforced, not trusted. Both calls run in restricted validation frames policed by a runtime tracer derived from ERC-7562: 13 rules forbidding block context, tx context, external account inspection, SSTORE/TLOAD/TSTORE, logs, CALL/CREATE and SELFDESTRUCT, permitting STATICCALL only to allowlisted precompiles and DELEGATECALL only to bytecode satisfying the same rules, validated RECURSIVELY (WIP1001-VR-9). A verifier is therefore a pure function of its own storage, its own code, its calldata, and the precompile allowlist. THE CONSEQUENCE FOR THIS AXIS: "Adding a new precompile to the validation allowlist is a hard-fork change." So although authentication is programmable, the set of CRYPTOGRAPHY a verifier can reach is closed by the protocol and widened only by hard fork. This is the direct opposite of zkSync Era, where the equivalent question has no closed answer (see chains/zksync-era) — and a third distinct answer from Base, which enshrines a closed authenticator set in the client with no user code at all. Three designs, three different places to draw the same boundary. Two further protocol-level oddities if it ships. Validation gas is NOT deducted from the envelope gasLimit and is charged instead against a per-block BLOCK_VALIDATION_GAS_BUDGET, so block capacity gains a second dimension and a 0x1D transaction that does not fit is DEFERRED rather than failed. And the failure classes give "failed" two meanings: a payload that REVERTS with an accepted policy is committed as a revert, while a payload the policy REJECTS is discarded — both after burning the nonce and charging a fee. If it ships, this row's key_binding becomes `account_code` for 0x1D and stays `derived` for every other type.
