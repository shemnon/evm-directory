Fork names and EIP sets diverge in both directions#

BSC activated Prague seven weeks before mainnet and Osaka five months after. Avalanche has P256VERIFY (an Osaka feature) without BLS12-381 (a Prague feature). At least thirteen ways a chain decides a feature is active#

"When does feature X become active on chain Y" has no general answer. Mainnet uses a timestamp. Polygon and Kaia use block numbers (CancunBlock, and Kaia's <Fork>CompatibleBlock, so a tool grepping for cancunTime finds nothing). OP Stack uses a timestamp whose equality with its own fork is ENFORCED at startup. Avalanche and Flare alias mainnet fork names onto their own timestamps (ShanghaiTime = durango). Arbitrum gates on an ArbOS version counter and short-circuits the timestamp path entirely. Monad gates its params ladder on the consensus ROUND, on a different axis from its timestamped EVM ladder. Sonic uses boolean flags in on-chain network rules, changed by a governed call and effective at the next epoch, with the block height recorded only after the fact. The Cosmos EVM family keeps the fork level in module state, movable by governance, with the real upgrade axis being named SDK upgrade handlers scheduled at a height. Moonbeam has no fork names, times, block numbers or client-side gate at all: the EVM ruleset is a constant inside a WASM runtime that governance replaces wholesale in state. Polygon zkEVM's forkID is not in the client — it is announced by an EVENT ON ETHEREUM L1, applies from a BATCH number, and is translated to an L2 block only at sync time; forkID 10 covered zero batches and still changed two consensus rules. zkSync Era ships upgrades as transaction type 0xfe carrying new system bytecode hashes, with no fork name or timestamp anywhere. Tron activates features by SR governance proposal. And Hyperliquid publishes no schedule at all — its small-block gas limit changed between block 10,000,000 and 20,000,000 with no fork to name. Reading a fork timestamp is not a general method; on much of this dataset there is no timestamp, and on some of it there is no client-side schedule to read.

EIP-1611 chains
ChainDetail & provenance
Auto EVM⚠️
modified silent divergence
Substrate's existential deposit sits underneath the EVM's account model and the EVM has no way to express it. `EXISTENTIAL_DEPOSIT = 1_000_000_000_000` wei (10^-6 AI3). An account whose balance falls below it is REAPED by `pallet-balances`: the remaining balance is handed to `DustRemovalHandler`, which burns it (`BlockFees::note_burned_balance`). EIP-161's rule is that an account is deleted only when it is empty AND touched; here it is deleted for being merely poor, and the residue is destroyed rather than kept. The mirror-image consequence is on the receiving side: `pallet-balances` refuses a transfer that would leave the RECIPIENT below the deposit, so a `CALL` with `value` under 10^12 wei to a fresh address fails where mainnet succeeds.
