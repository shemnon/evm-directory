Always pushes 0. `applyMessage` sets `msg.GasPrice`, `msg.GasFeeCap` and `msg.GasTipCap` to zero before every execution because "gas fee is set by ISC", and the tx context is built from that zeroed message. ADDED AT GENESIS AND REMOVED AT T1C — the only opcode in this dataset that a chain invented and then withdrew. It pushed `block.timestamp` in MILLISECONDS for 2 gas. The instruction table installs it only while `!spec.is_t1c()`, so from 2026-03-12 the opcode is undefined again and contracts compiled against it fail with an invalid-opcode error. Mainnet has never assigned 0x4F. Recorded under `removed` because that is its state at the baseline; the note is the whole finding.
n/aTempo⚠️SSTORE
Repriced twice and then given a Tempo instruction. TIP-1000 (T1+): a 0->nonzero SSTORE costs 250,000 gas, 12.5x mainnet's 20,000. TIP-1060 (T7+): the gas function charges only a 5,000-gas residual and the SSTORE opcode is REPLACED in the instruction table by `gas_credits::sstore`, which mints and spends storage credits at the StorageCredits precompile — a slot clear mints a 245,000-gas credit instead of a refund, and a later creation by the same account consumes it. `sstore_clearing_slot_refund` is 0.
n/aTempo⚠️CREATE
500,000 gas from T1 — 15.6x mainnet's 32,000 — under TIP-1000, on the argument that contract creation is permanent state. Account creation is 250,000 (mainnet 25,000) and CODEDEPOSIT is 1,000 (mainnet 200 per byte, i.e. Tempo makes it a flat fee). The TIP-1016 "regular vs state gas" split that would decompose these is implemented in `amsterdam_gas_params` but is gated behind `cfg.enable_amsterdam_eip8037`, which is set only in tests — so at the probe block the T1 flat costs are what applies.

n/aTempo⚠️CALL
The value argument is structurally unusable: no account can ever hold a nonzero native balance, so any CALL carrying value fails for insufficient funds. For 0x76 transactions the check is earlier and harder — every entry in `calls[]` is rejected at validation with `ValueTransferNotAllowedInAATx` if `value != 0`, before execution begins.
n/aArc⚠️SELFDESTRUCT
Replaced in the instruction table by an Arc implementation with three layered behaviours: blocklist checks on both the executing address and the beneficiary (failing with "Blocked address"), a transfer log on any non-zero balance move (a Circle-specific `NativeCoinTransferred` before Zero5, an EIP-7708 `Transfer` from Zero5), and rejection of a self-targeted selfdestruct that would increase the account's own balance. Three variants across Zero5/Zero6/Zero7.
n/aArc⚠️CALL
Value transfers work normally — Arc HAS a native coin, unlike tempo. What changes is that a value-bearing transaction is rejected pre-execution if either party is blocklisted, and that a plain CALL does NOT emit the EIP-7708 log the precompile paths emit. See gotchas.
