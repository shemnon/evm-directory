Notes 2#

Variation among OP Stack descendants#

OP Mainnet's delta file is empty. Base, on the same stack and client version, reimplements the EVM layer in Rust and adds five fixed precompiles, a dynamic precompile range, native account abstraction (EIP-8130) with its own type byte 0x79, and four chain-specific forks. opBNB carries BSC's precompiles and is pinned three fork generations back. Celo adds type 0x7b (CIP-64, gas paid in an ERC-20), which accounts for 61% of transactions in the blocks sampled. Resolving ethereum → op-stack → X does not determine X's type-byte set.

OP Mainnet · Base · opBNB · Celo · World

Same consensus engine, opposite failure mode — the Engine API is the discriminator#

Berachain and Artela both run CometBFT and both must answer what happens to a transaction that is in a proposal but invalid when it executes. They answer oppositely, and the discriminator is not the consensus engine but where the EVM runs. Artela's EVM is in-process behind an ante-handler chain, so failure is per-transaction: the transaction is erased, provably in the CometBFT block yet with no index entry and a permanently null receipt. Berachain's EVM is a separate process reached over the Engine API, whose engine_newPayload verdict covers the whole payload with no per-transaction skip, so failure is per-block — ProcessProposal returns PROCESS_PROPOSAL_STATUS_REJECT, CometBFT re-proposes the height, and an RPC client observes nothing at all. Berachain goes further: CometBFT never orders EVM transactions in the first place, since prepareProposal ignores req.Txs and returns exactly two entries, the SSZ beacon block and its blob sidecars. Any generalisation of the form "Cosmos/CometBFT chains behave like X" is wrong in one of the two directions; the question to ask is whether the EVM is inside the ABCI application or behind the Engine API.

ev-reth v0.5.2 pins reth as a Cargo dependency and adds crates around it; it does NOT vendor a modified interpreter. The EVM opcode/gas semantics are upstream reth's. Cosmos EVM (evmd)—
The EVM is NOT vendored. go.mod requires github.com/ethereum/go-ethereum v1.16.8 and then REPLACES it with github.com/cosmos/go-ethereum v1.17.2-cosmos-0 (go.mod, the `replace` block). So the interpreter, the jump table, the 0x01-0x11 precompile implementations, the gas table and params.ChainConfig all come from a geth at 1.17.2 — which has Osaka — while the framework only ever installs the PRAGUE precompile map (precompiles/types/static_precompiles.go:WithPraguePrecompiles) and DefaultChainConfig leaves OsakaTime nil. Osaka is therefore REACHABLE by configuration here (the field exists and the dependency implements it), unlike Sei, whose geth fork has no Osaka branch at all. That distinction — "not activated" vs "not representable" — is the one SCHEMA.md's sync_point note is about, and Cosmos EVM sits on the good side of it.
Injective
INJECTIVE DOES NOT DEPEND ON cosmos/evm. `grep cosmos/evm go.mod` returns nothing; the EVM lives at injective-chain/modules/evm/ as a vendored fork of the shared Ethermint/cosmos-evm tree, so every upstream change has to be hand-carried. Four measurable consequences, all older than the framework row: (1) THE DEPRECATED PROTOBUF ENCODING IS STILL IN THE WIRE FORMAT. cosmos/evm v0.7 writes `reserved 1, 2, 3, 4` in MsgEthereumTx; Injective still declares `data` (Any of LegacyTx/AccessListTx/DynamicFeeTx), `size`, `deprecated_hash` and `deprecated_from` alongside `raw`. ValidateBasic now rejects all four, and AsTransaction still falls back to unpacking `data` when `raw` is empty, so both decoders remain reachable for historical data. (2) NO x/feemarket. Injective uses its own txfees module (an Osmosis "Mempool1559" port) instead, and there is no EIP-1559 base fee in the EVM at all — see eips.1559. (3) NO ACTIVE-PRECOMPILE PARAM AND NO 0x0800 BLOCK. The framework's two-step registration (build the map, then list the address in ActiveStaticPrecompiles) does not exist here; Injective hard-wires four CustomContractFn closures at app construction. Its precompile set is therefore NOT per-deployment optional, and the framework's 0x0100/0x0400/0x0800-0x0807 addresses are all empty on Injective — verified live. (4) NO OsakaTime FIELD. The ChainConfig proto stops at PragueTime, so Osaka is not merely unscheduled but unrepresentable — Injective is on the Sei side of the line the cosmos-evm row draws, not the framework's.
Artela
ARTELA DOES NOT DEPEND ON cosmos/evm, AND NEVER DID — `grep cosmos/evm go.mod` returns nothing. The EVM module is a copy of the Ethermint tree with every identifier renamed: `x/evm` and `x/fee` are Ethermint's `x/evm` and `x/feemarket`, and the protobuf packages are Ethermint's with the word swapped — `artela/evm/v1`, `artela/fee/v1`, `artela/types/v1`, `artela/crypto/v1/ethsecp256k1` where Ethermint writes `ethermint/...`. The rename is complete enough that a case-insensitive grep for "ethermint" over the whole tree returns NOTHING; the one surviving fingerprint is a comment in the RPC layer reading "NOTE: Evmos doesn't have a storage hash". Establishing the lineage therefore takes the proto layout, not a string search, and treating Artela as an independent Cosmos EVM would have been wrong. THE FORK POINT IS OLD, AND THAT IS MOST OF THE DELTA. go.mod pins Cosmos SDK v0.47.4 (itself replaced by a fork, see client.companion_repos), CometBFT v0.37.2 and go-ethereum v1.12.0 — an Ethermint of roughly mid-2023, three years behind the cosmos-evm row's v0.7.2. Five consequences, each of which OVERRIDES an inherited fact: (1) ABCI 0.37, NOT ABCI++ 0.38. There is no FinalizeBlock on this chain. Execution is BeginBlock / DeliverTx-per-transaction / EndBlock / Commit. Any statement about Cosmos EVM ordering phrased in terms of FinalizeBlock has to be re-read one ABCI version back — see consensus. (2) NO x/erc20 MODULE. There is no token-pair registry, no MsgConvertERC20 / MsgConvertCoin, no dynamic ERC-20 precompiles and no IBC-packet-creates-a- precompile path. The ancestor's `precompiles.dynamic_range` and its `ibc_recv_erc20_registration` system transaction DO NOT EXIST here. (3) NO COSMOS PRECOMPILES AT ALL. There is no `precompiles/` package, no ActiveStaticPrecompiles param and no two-step registration. The entire 0x0100 / 0x0400 / 0x0800-0x0807 block the ancestor documents is absent, and the precompile set is exactly go-ethereum v1.12.0's — 0x01..0x09. Artela is the counter-example to the assumption that a Cosmos EVM chain exposes staking and IBC to bytecode. (4) NO PREINSTALLS MECHANISM AND NO MsgRegisterPreinstalls. Genesis bytecode is installed by a CLI subcommand at chain setup (`artelad add-genesis-contract`), not by a governance message, so the ancestor's "governance can install bytecode at any address at any time" does not hold. (5) THE FORK SCHEDULE IS BLOCK-NUMBERED, INCLUDING SHANGHAI AND CANCUN. ChainConfig has `ShanghaiBlock` and `CancunBlock`, not `ShanghaiTime` / `CancunTime`; the timestamps geth needs are SYNTHESISED per call as 0 or MaxUint64 from a height comparison. There is no Prague or Osaka field, so neither is schedulable — Artela is on the Injective side of the "not activated vs not representable" line, one fork earlier.
