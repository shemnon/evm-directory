the envelope

The EIP-2718 envelope 0x00–0x04 (Legacy, 2930, 1559, 4844, 7702) is shown for every chain, from an envelope each row declares: = accepted in mainnet shape, ➖ not accepted. Turn on hide rows where every chain agrees to collapse the types no chain diverges on. Rows above 0x04 list only the chains that define a byte there.

Notes 3#

Type-byte allocation from both ends of the range#

EIP-2718 permits 0x00–0x7f. Mainnet allocates upward from 0x00; other chains allocate downward from the ceiling — zkSync 0x71, Arbitrum and Kaia both 0x78, Base 0x79, Celo 0x7b and 0x7c, the OP family 0x7d and 0x7e, Polygon 0x7f. There is no registry between the two frontiers. Current occupancy is computed from the data on the transaction types axis. Kaia's type numbers do not fit in a byte at all: they are uint16 (0x7801–0x7804), and Ethereum transactions are re-wrapped as 0x78 || ethType || rlp, so the RPC representation is standard while the consensus encoding is not.

Arbitrum · Base · OP Stack · Polygon · Celo · Kaia · zkSync

Transactions outside the EIP-2718 envelope#

Avalanche's atomic import and export transactions (UTXO, Avalanche codec) and all 43 of Tron's protobuf contract types carry no EIP-2718 type byte. Two chains with no shared ancestry required the same non_evm_transactions schema section. An indexer enumerating transactions through the EVM envelope does not see Avalanche's cross-chain value movement.

What counts as "the same transaction" is not the same question on every chain#

Where many proposers build blocks at once, the same transaction landing in more than one block is the normal case rather than an edge case, and the dataset holds three mechanisms operating at three different layers. Taraxa deduplicates at period assembly, before the ordered block set becomes a transaction list: the duplicate never executes, but the DAG block carrying it stays in the period data, so it remains visible in the DAG and is absent only from the executed list. Conflux executes it, gets OldNonce, marks it Skipped, and then erases every trace — from the block body, the transaction index and eth_getTransactionReceipt alike, so the duplicate is indistinguishable from a transaction never submitted. Taraxa credits fees strictly to the first includer and, before its Aspen fork, gave a DAG block no reward at all unless it contributed a unique transaction: nobody is charged and nobody is slashed, and the only cost of losing the race is forgone revenue. Where deduplication happens — before ordering, or after execution — determines what a client can observe, and the two are not interchangeable. Hedera makes the identity model itself the divergence. A transaction there is keyed by TransactionID = (payer account, valid-start timestamp) — nothing about the contents enters the key, so two byte-identical submissions with different valid-starts are different transactions and two unrelated bodies sharing a payer and timestamp are the same one — and uniqueness holds only inside a 180-second window, after which an ID may be reused. Duplicates are the designed-for case, because the SDKs submit to several nodes for reliability. Hedera then does what no other row does: it charges for them. A duplicate first seen from another node debits the payer the node and network fees with the service fee waived and never executes; a duplicate from the same node debits that node instead; and the node that lost the race is paid the node fee, so losing is revenue. None of it is visible to Ethereum tooling — the Ethereum hash is recorded only inside the handler a duplicate never reaches — so an operator sees an HBAR debit with no eth_* object to attribute it to. Taraxa charges nobody, Conflux erases everything, Hedera bills silently. Sonic dedupes in four layers and the layer that applies depends on an on-chain toggle: an emitter-side stake lottery, a seenHashes pass over the confirmed event set during block derivation, and a nonce precheck at execution — but its SingleProposerBlockFormation mode bypasses the hash dedup entirely, leaving only trial-execution at the proposer. The duplicate vanishes from eth_* exactly as on Conflux, yet dag_getEventPayload still lists it one level down, exactly as on Taraxa; the whole fee is credited to the first ordered event's creator and the losing emitter is unrewarded but not slashed. Monad is the strong negative: no deduplication anywhere, because a block containing a duplicate is rejected. Two consensus checks do it — a within-block nonce_usages set, and a cross-block coherency check that reconstructs expected nonces from the triedb at N-3 plus the NonceUsageMap of every uncommitted ancestor, which is what deferred execution forces. Autonomys deduplicates by byte equality across the concatenation of every valid bundle, after per-bundle validity classification — so an ordinary duplicate is explicitly not one of InvalidBundleType's six variants and its author is never slashed. That is the inversion worth noting: on the one chain where a stale nonce inside a bundle is a slashable protocol violation, submitting the same transaction twice is not.

Avalanche C-Chain#

Atomic transactions move value between the C-Chain and Avalanche's X/P chains. Cosmos EVM (evmd)#

THE INVERSION. SCHEMA.md defines this section as "protocol transactions with no EIP-2718 type byte at all" — Avalanche's UTXO atomic transactions, Tron's 43 protobuf contract types. Cosmos EVM turns it inside out: here it is an EIP-2718 transaction that is itself WRAPPED in something with no type byte. A user signs an ordinary RLP 0x02 transaction; a node wraps it in `MsgEthereumTx`, which is wrapped in a Cosmos SDK `TxBody`, which is what CometBFT hashes and orders. Anything reading blocks at the consensus layer sees protobuf; the Ethereum view is reconstructed by the rpc/ package. HOW THIS DIFFERS FROM TRON, which is the existing protobuf precedent. Tron's transactions ARE protobuf all the way down — there is no RLP envelope anywhere and no Ethereum transaction to recover. Sei is closer but still different: it re-encodes the Ethereum transaction's FIELDS as protobuf TxData inside MsgEVMTransaction, so the RLP bytes do not survive. Cosmos EVM v0.7 keeps the raw envelope verbatim: `MsgEthereumTx.raw` is `bytes` with gogoproto customtype EthereumTx, whose Unmarshal is literally geth's Transaction.UnmarshalBinary. So the EIP-2718 envelope IS present, byte-exact, one protobuf field down — and the proto file's `reserved 1, 2, 3, 4` records that the older field-by-field encoding was removed to get there. The transaction hash Ethereum tooling knows is the keccak of those inner bytes; CometBFT's transaction hash is the sha256 of the outer protobuf, and the response type says so in a comment. A consequence worth stating plainly: the outer Cosmos transaction has its own fee amount, gas limit and signer list, all of which are set from the inner Ethereum transaction by BuildTx and none of which are signed by the Ethereum signature. Authorization comes entirely from the inner envelope — see tx_authorization.

Artela#

THE SAME INVERSION THE ANCESTOR DESCRIBES, ONE GENERATION EARLIER AND ONE STEP WORSE. A user signs an RLP transaction; the node wraps it in MsgEthereumTx, which is wrapped in a Cosmos SDK TxBody, which is what CometBFT hashes and orders. Moonbeam#

Every EVM state transition on this chain arrives inside a Substrate extrinsic — the Ethereum envelope is the guest here, not the host. Moonbeam shows BOTH shapes the dataset has met: an EIP-2718 payload surviving byte-exact inside another encoding (the cosmos-evm shape) and a native non-Ethereum call that produces EVM execution (the Tron shape). It also closes the obvious third path: `pallet_evm::Call::call`, the textbook "Substrate extrinsic that calls the EVM pallet", is unreachable by anyone because the runtime call filter has `RuntimeCall::EVM(_) => false` unconditionally, with a comment citing re-entrancy.

Checked, and there are none#

Kaia — None. Unlike Tron, Avalanche or Sei, every Kaia transaction carries a leading type number and is RLP-encoded. The divergence is in the SHAPE of the type space, not in transactions escaping it.

Taiko Alethia — NONE — and the negative is worth recording, because the anchor is the closest thing in this dataset to a case that belongs here and does not. SCHEMA.md's `non_evm_transactions` is for protocol transactions with NO EIP-2718 type byte at all (Avalanche's UTXO atomic txs, Tron's protobuf contracts). Taiko's anchor has a type byte — mainnet's 0x02 — and is decoded by an unmodified EIP-2718 decoder into an unmodified DynamicFeeTx. It is recorded in tx_types (as a positional modification of 0x02) and in system_transactions (as the protocol-driven state change it is), and deliberately NOT here.

Taiko⚠️
modified silent divergence
THE finding of this row, and the reason it appears here AND in system_transactions. Taiko's protocol transaction did not take a byte from the 0x7f ceiling the way Arbitrum (0x78), Base (0x79), OP Stack (0x7e), Celo (0x7b) and Polygon (0x7f) did. It wears mainnet's OWN type 0x02, and nothing in its encoding distinguishes it: `MarkAsAnchor` is applied to `i == 0` and to nothing else. The transaction is identified by its INDEX, not by its bytes. At index 0 the rules of type 0x02 change: the balance check is skipped and the up-front gas debit is set to zero, the gasFeeCap-vs-baseFee check is skipped, returnGas is skipped, and the base-fee split to treasury and coinbase is skipped. A type 0x02 transaction at index 0 therefore pays NO GAS AT ALL — while its receipt reports effectiveGasPrice equal to the base fee and gasUsed of 112,068, so a fee-accounting tool that multiplies the two invents a fee that nobody paid and no account lost. Anywhere other than index 0, type 0x02 is exactly mainnet's. So this is not a new type byte and not a new envelope — it is a POSITIONAL override of a mainnet type byte, a shape the type-byte axis has no way to express.

0x7eDepositTx (Mantle variant)1 chains
ChainDetail & provenance
Mantle⚠️
modified silent divergence
OVERRIDE of the op-stack entry per SCHEMA.md's override-by-key rule. OP's deposit is eight RLP fields; Mantle's is ten, and the ninth is not appended — `EthValue` is INSERTED at position 7, where OP Stack's decoder expects `Data`. `EthTxValue` is `rlp:"optional"` on the end. The two fields exist because the gas asset changed. `Mint` still creates the NATIVE asset, which on Mantle is MNT. ETH is demoted to an ERC-20 at 0xdEAd..1111, and `EthValue`/`EthTxValue` are how the deposit moves it — not by calling that token, but by the client writing its balance slots directly (see system_transactions). Hazard direction matters: an OP-Stack decoder handed a Mantle deposit sees a ten-element list where it expects eight and errors, so this fails loudly on the wire. What does NOT fail loudly is the JSON: a Mantle deposit serialises with an extra `ethValue` key that OP tooling silently drops, and the value it drops is a mint of a different asset.
0x7eL1MessageTx1 chains
ChainDetail & provenance
Scroll➕
added silent divergence
A THIRD, INDEPENDENT CLAIMANT TO 0x7e. OP Stack's deposit transaction and Scroll's L1 message transaction are the same type byte, different RLP payloads, different field counts, no shared code. The dataset already records 0x7e as "the OP family"; it is not. Scroll's payload is (QueueIndex, Gas, To, Value, Data, Sender) — six fields, no chain id, no signature, no nonce, no gas price, and `To` may not be nil (no contract creation from L1). A decoder that sees 0x7e and reaches for OP's DepositTx layout mis-parses every L1 message on Scroll. Two further traps: the JSON carries non-standard `sender` and `queueIndex` keys, and the type is invisible in ordinary traffic — a 50-block census at the probe height found 40 legacy and 11 dynamic-fee transactions and ZERO 0x7e, and a 389-block sweep found none either, so an integration can pass every test and still meet this type in production.
0x7ePoLTx (BRIP-0004 Proof-of-Liquidity distribution)1 chains
ChainDetail & provenance
Bera➕
added spec: BRIP-0004 fork: prague1 silent divergence
DIRECT COLLISION WITH OP STACK'S DEPOSIT TYPE. Seven fields, no signature (rawSignatureValues returns 0,0,0), sender hardcoded to the system address 0xfff..ffe, `to` fixed to the PoL Distributor from chain config, and `nonce` abused to carry the BLOCK NUMBER BEING DISTRIBUTED FOR (block-1), not an account nonce. Its calldata is always distributeFor(bytes pubkey) over the PARENT block's proposer BLS key, taken from the parent header's 22nd field. Three consensus rules make it unusual even among protocol transactions: (1) it MUST be transaction index 0 of every post-Prague1 block and MUST NOT appear anywhere else — validate_pol_transaction recomputes the expected transaction and compares HASHES, so the entire transaction is a pure function of (chain id, distributor, block number, base fee, parent proposer key); (2) it consumes ZERO block gas despite running with a 30,000,000 gas limit and emitting logs — at the probed block its receipt shows gasUsed 0 with 41 logs, and cumulativeGasUsed for the block excludes it entirely; and (3) it is rejected by the transaction pool, so it can never be submitted. The receipt is a normal typed receipt, so an indexer summing receipt gasUsed agrees with the header while an indexer summing traced execution does not.
