Same-address divergence, and every flavour is quieter than enumeration#

An address that exists on two chains can differ in ways no address diff sees, and every one of those flavours is quieter than adding or removing the address.

Supplies a detection channel the other flavours lack: disabled precompiles stay in the map and so stay WARM (122 gas) while genuinely absent addresses are COLD (2622), which separates the two cases by gas alone.

P-256 verification returns empty output on five chains, for five reasons#

EIP-7951 signals an invalid signature by returning empty output — byte-identical to what a call to an absent precompile returns. Where 0x0100 is empty, every P-256 verification against it reports "invalid" with no revert and no error, and a passkey wallet ported there is broken but looks merely strict.

P256VERIFY is implemented as p256Verify_zkevm and present only in a forkID that has never activated, so 0x0100 answers empty.

At least thirteen ways a chain decides a feature is active#

"When does feature X become active on chain Y" has no general answer. Mainnet uses a timestamp; reading a fork timestamp is not a portable method, because on much of this dataset there is no timestamp and on some of it no client-side schedule to read at all.

The forkID is not in the client. It is announced by an EVENT ON ETHEREUM L1, applies from a BATCH number, and is translated to an L2 block only at sync time — and forkID 10 covered zero batches while still changing two consensus rules.

A second resource meter, and five ways it fails your transaction#

Gas is no longer the only thing a transaction can run out of, and the failure modes share nothing. A transaction can be rejected, truncated away, silently dropped, or charged for work it never did, and only one of those is visible as an ordinary revert.

Discards with no receipt — no revert, no charge, and the hash is blacklisted from the pool afterwards.

Forks#

THE ONLY ACTIVATION MECHANISM IN THIS DATASET THAT IS NOT IN THE CLIENT AT ALL. The Ethereum ladder is frozen at Berlin by a chainspec of sentinels; everything that actually changes is gated on forkID, a small integer that is announced by an EVENT ON ETHEREUM L1 (UpdateZkEVMVersion / rollup-manager upgrade), applies from a BATCH number, and is only translated into an L2 BLOCK number at sync time by UpdateZkEVMBlockCfg reading the node's local L1-derived database. cdk-erigon ships no fork schedule for chain 1101 — hermez.json contains not one forkID field. A node's own chain.Config fork blocks are constructed at runtime from what it saw on L1. Consequences the other five mechanisms do not have: (a) the fork schedule is mutable from L1 with no L2 client release; (b) the canonical unit is the batch, and the block number is derived, so "which fork was block N on" is answerable only by a node that has synced L1; (c) a forkID can be SKIPPED, and one was — forkID 10 has zero batches, and UpdateZkEVMBlockCfg silently assigns it the previous fork's block number ("using last set block number"), so IsForkID10() is true from forkID 9's block for a fork that never happened. Compare: OP Stack enforces timestamp equality, Avalanche assigns timestamps, Arbitrum gates on ArbOS version, Polygon PoS on block numbers, Moonbeam swaps a WASM blob with no version at all. forkID is an L1 event indexed by batch.

Precompiles 18#

ZERO added addresses. Three tombstones, and the tombstones are the whole story. Two structural points worth carrying into the aggregate tables: (1) The disable switch is a FIELD ON THE PRECOMPILE, not a missing map entry: &bigModExp_zkevm{enabled: false}. The address stays in the map, so it stays in the warm access list, so it stays cheap to touch — and it reverts. That is why the gas signature above works. (2) Polygon's tombstone fails DIFFERENTLY from Scroll's. Both chains disable RIPEMD160 and BLAKE2F for prover reasons; Scroll's disabled precompiles raise a non-revert error that BURNS ALL FORWARDED GAS, and its 0x03 is even charged the full RIPEMD160 price before failing. Polygon's raise an error that IsErrTypeRevert() treats as a revert: nothing is pre-charged and every forwarded wei of gas comes back. Two chains, the same three-precompile decision, opposite gas semantics. A caller that wraps the call in a try/catch survives on Polygon and is drained on Scroll. And nothing here is a per-block work budget: unlike Linea, which lets RIPEMD160 run in eth_call and vetoes it at block-building time, Polygon's disabled precompiles fail identically in eth_call and on chain. HOW THE COUNTERS FAIL, characterised against the other rows that have a second meter. A transaction whose counters overflow is NOT reverted, NOT charged, and gets NO RECEIPT — CheckForOverflow returns true, the sequencer removes the attempted counters, marks the sender as skipped for the rest of the batch, and moves on. SingleTransactionOverflowCheck then re-runs it alone against an empty batch; if it still overflows, the hash is passed to handleBadTxHashCounter, which increments a persistent per-hash counter, and the transaction is discarded from the pool. Gotchas 11#

  • BLOCKHASH RETURNS THE STATE ROOT. Not the block hash — the state root of that block, read out of a storage slot. Both are 32 bytes, nothing reverts, and the value looks entirely plausible. Verified at block 33391890: BLOCKHASH(33391889) equals that block's `stateRoot` and not its `hash`. Commit-reveal, randomness and anchoring contracts ported here are wrong and silent.
  • MODEXP (0x05) IS DISABLED AND USED NOT TO BE. It worked at forkID 7 Etrog and stopped working at forkID 8 Elderberry, block 10742147. RIPEMD160 (0x03) and BLAKE2F (0x09) have been disabled since Etrog. All three REVERT — they do not return empty — and the caller keeps its forwarded gas, which is the opposite of Scroll's identical-looking decision. RSA verification, some BLS libraries, and anything using modexp for a modular inverse are dead here.
  • THE FORK AXIS IS AN L1 EVENT, NOT A TIMESTAMP OR A BLOCK NUMBER. forkID is announced on Ethereum, applies from a BATCH number, and is turned into an L2 block number only by a node that has synced L1. The client ships no fork schedule for chain 1101 at all. There is no field to read, and `eth_getBlockByNumber` tells you nothing about which semantics were in force. Use zkevm_getForks.
  • FORK ID 10 NEVER HAPPENED, AND STILL CHANGED THE RULES. It has zero batches, but UpdateZkEVMBlockCfg assigns any unannounced forkID the previous fork's block number, so every `IsForkID10()` gate in the client — including the end of the "code must not end in PUSH1" rejection and a doubling of the prover step budget — became true at forkID 9's block. Skipped forks are not no-ops.
  • EVENT LOG DATA WAS CORRUPTED BY CONSENSUS FOR BLOCKS 10742147-19175238. `applyHexPadBug` hex-encodes the last 32-byte word of a log's data, strips leading '0' characters at the string level, then re-pads — mangling the tail of any log whose data is not a multiple of 32 bytes. Before that range the data was zero-padded to 32; after forkID 12 it is untouched. Three encodings of the same field, and the middle one is a bug the chain froze rather than fixed.
  • EXTCODEHASH RETURNS ZERO FOR EVERY CODELESS ACCOUNT, funded or not, where EIP-1052 distinguishes "exists with no code" (keccak256 of empty) from "does not exist" (zero). Contract-detection and account-existence checks silently invert.
  • SELFDESTRUCT DOES NOT DESTROY ANYTHING. It sends the balance and stops. Code, storage and nonce survive, and the account keeps answering calls. EIP-6780 is explicitly commented out in the source to preserve this.
  • THE FEE YOU SIGN IS NOT THE FEE YOU PAY. The sequencer attaches a one-byte "effective gas price percentage" and the state transition rewrites gasPrice, feeCap and tip to signed*(ep+1)/256 before execution. Read effectiveGasPrice from the receipt; do not compute it.
  • NO EIP-1559 AT ALL. The header has no baseFeePerGas field, BASEFEE is an invalid opcode, and type-0x02 transactions are rejected from the pool as UnsupportedTx. The chain accepts exactly transaction types 0x00 and 0x01.
  • THE STATE TRIE IS A POSEIDON SMT, NOT AN MPT. stateRoot is a field element and eth_getProof does not produce an Ethereum-verifiable proof. Bridges and light clients that verify storage proofs against a Keccak MPT cannot verify anything here.
  • THE CHAIN APPEARS TO HAVE STOPPED. The head has been block 33391890, timestamped 2026-07-03, for 52 days across two independent endpoints, and 30,593 batches were produced but never sequenced to L1 — so five and a half million blocks sit above the last finalized one with no proof behind them. Whether this is a sunset or an outage is not established here, but any integration should check liveness before assuming the network is running.

  • the canonical unit is the batch, and the block number is derived, so "which semantics applied at block N" is answerable only with an L1-synced node;
  • a forkID can be skipped, and one was.

4. BLOCKHASH returns the state root

The sharpest silent divergence on this chain, and it is not a precompile.

Worse, the value is not even the same kind of hash. 6. Event log data was corrupted by consensus for 8.4 million blocks

ApplyPaddingToLogsData has three regimes, on a forkID axis:

  • forkID 4–7: data zero-padded at the end to a multiple of 32.
  • forkID 8–11 (blocks 10,742,147 – 19,175,238): applyHexPadBug — hex-encode the last 32-byte word, right-pad the string to 64 characters, strip leading '0' characters, re-prepend zeros, truncate. A nibble-level shift that mangles the tail of any log whose data length is not a multiple of 32.
  • forkID 12: if isForkId12 { return } — no transformation. The bug is gone.

The function is named applyHexPadBug. It is a bug the chain froze into consensus for four forkIDs and then dropped. An indexer re-deriving logs across that range must reproduce the bug to match the chain. Log indexing changed too: forkID 4–7 restart logIndex at zero per transaction rather than per block.

A related receipt divergence with the same shape: before forkID 8, CreateReceiptForBlockInfoTree forces status = 1 on any receipt whose execution error was ErrUnsupportedPrecompile — a transaction that reverted on a disabled precompile was recorded as successful in the proven block-info tree. The batch encoding has its own, incompatible one-byte type space: legacy transactions are written as bare concatenated fields with no envelope, fullRlpTxType = 15 prefixes a typed transaction, and 11 introduces a 9-byte changeL2Block record that creates block boundaries. 8. Two meters, and the fee you sign is not the fee you pay

Effective gas price. The sequencer attaches a one-byte percentage to every transaction and the state transition rewrites gasPrice, feeCap and tip to signed × (ep+1) / 256 before execution, from forkID 5 onward (CalculateEffectiveGas, GetTxContext). ep = 0 charges 1/256 of the signed price. The byte travels in the L1 batch data, so it is consensus, not policy. A signature over a gasPrice is not a commitment to that gasPrice here; read effectiveGasPrice from the receipt rather than computing it.

Eight zk counters. totalSteps, arith, binary, memAlign, keccaks, padding, poseidon, sha256, budgeted per batch, with the budget a function of forkID: totalSteps is 2^23 below forkID 10, 2^24 at 10, 2^25 from 11, minus 200 and then minus a safety margin. The margin is 5% by default, 2.5% at forkID 10, 1.25% at forkID 11 — and safetyPercentages has no entry for forkID 12, so the live fork falls back to the 5% default. The margin tightened at 11 and loosened again at 12, silently, because a map was not updated. The other seven limits are fixed ratios of totalSteps (arith = steps>>5, keccaks = floor(steps/155286)*44, poseidon = floor(steps/31)…).

How the second meter fails, characterised against the other rows that have one:

A transaction that overflows counters is not reverted, not charged, and gets no receipt. CheckForOverflow returns true, the sequencer discards the attempted counters, marks the sender skipped for the rest of the batch, and moves on. SingleTransactionOverflowCheck then re-runs it alone against an empty batch; if it still overflows, handleBadTxHashCounter increments a persistent per-hash counter and the transaction is discarded from the pool.

That is Linea's shape (unminable, cached as bad) rather than Taiko's (block truncated, stays valid) or Moonbeam's (surfaces as OutOfGas with EVM gas left). It differs from Linea's in the resource — Linea budgets arithmetization lines per block, Polygon budgets prover steps per batch — and in one way that matters practically: Linea uses zeroed budgets as a feature switch, making specific precompiles permanently unminable while they still work in eth_call. Polygon put its permanent refusals in the precompile map instead, so its counters are purely a size limit. Gas is irrelevant to the outcome either way: a perfectly funded transaction simply never appears.

9. SELFDESTRUCT does not destroy anything

Balance moves, then STOP. No deletion mark, no code clearing, no storage clearing, no nonce reset. A self-destructing proxy ported here keeps its code and keeps answering calls after "destruction".

Related trap: cdk-erigon defines opcode 0xfb as SENDALL in the disassembler and then wires it to INVALID in the live instruction set. The mnemonic exists; the opcode does not. A tracer will label an invalid opcode as a valid one.
